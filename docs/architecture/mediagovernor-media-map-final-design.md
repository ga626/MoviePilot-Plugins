# MediaGovernor 最终重设计：媒体地图与增量治理

> 状态：设计冻结草案。本文只定义下一份 PR；本轮没有读取真实媒体、修改插件、调用模型或写入 NAS。

## 先说结论

插件不应再从“失败历史有多少条”开始猜问题。它要先建立一张**当前文件地图**：下载区现在有什么，媒体库现在有什么，它们之间有哪些可证明的关系。整理历史只是一条辅助线索，不能代替当前事实。

这张地图第一次建立会慢，但只做一次全量盘点。以后只重读新发生或已变动的部分；没有变化就复用旧结果。这样才能同时抓住两件事：

1. 原生整理真的失败：原始文件还在，但没有得到应有的媒体库结果。
2. 原生整理表面成功、实际错误：硬链接存在，但作品、分类、季、集或目录结构与应有结果不符。

旧版的“47 条未恢复失败”不能当作第一类问题的数量。它只是 `history/transfer?status=false` 返回的历史线索，未逐个验证原始文件和目标文件是否仍存在，也漏掉插件启用前就已“成功但分错”的记录。新版不保留这个口径。

## 先统一四个名字

- **下载单元**：一次下载留下的顶层文件或顶层目录；可能是一部电影、一季剧，也可能是合集。
- **文件集合**：下载单元中实际存在的视频、字幕、NFO 和目录层级。
- **作品单元**：最终应该被整理成一部电影，或一部剧/动漫的一季及各集。一个下载单元可以拆成多个作品单元。
- **媒体库结果**：媒体库中当前存在的对应硬链接和目录结构。

历史的一条记录通常只对应一个文件的一次整理，不等于下载单元，也不等于一部作品。地图以“下载单元 → 作品单元 → 媒体库结果”为主线。

## 能调用什么，不能调用什么

### 已有能力：本 PR 可以使用

| 目的 | MoviePilot 已有入口 | 本方案怎样用 |
| --- | --- | --- |
| 找到受管下载区和媒体库 | `GET storage/directories?directory_type=download`、`library` | 只以当前配置返回的目录为根，不写死路径；界面只显示配置名称和类别。 |
| 读取当前文件事实 | `POST storage/list` | 逐层读取目录，得到 `FileItem` 的名称、类型、大小、修改时间等；首次递归，之后只深入指纹变化的分支。 |
| 读取历史关系 | `GET history/transfer` | 取成功和失败历史的源、目标、模式、媒体身份、下载 hash；只做关联、解释和旧目标定位。 |
| 原生身份识别 | `GET media/recognize_file` / `media/recognize` | 先走原生识别；模型只能提出标题线索，最终仍要回到原生识别得到 `media_source + media_id`。 |
| 核对“应该整理成什么样” | `POST transfer/manual/target-path`、`transfer/manual` 的 `preview=true` | 对已确认身份的源文件要求官方生成逐文件预览；预览才是应有目录、分类、季集和命名的权威计算。 |
| 找到可重建的旧目标 | `POST transfer/manual/history`、成功历史的 `dest_fileitem` | 只针对本次源文件及其确实命中的成功历史取旧目标，绝不按名称猜删。 |
| 删除错误硬链接并重建 | `POST transfer/manual`，带成功历史 `logid`、非 preview、`reorganize=false` | 由 MoviePilot 在同一官方整理计划内清理这条旧目标，再从原始来源重新建立；插件不直接调用 `storage/delete`。 |
| 长期保存地图 | `get_data_path()`/`save_data()` | 先用插件私有 `media_map.json` 保存有界地图，少量 salt、缓存和脏项进插件数据；都在 NAS 插件私有持久区，不进源码、Git、报告或通知。 |
| 取得新整理变化 | `app.sdk.events` 的 `TransferComplete`、`TransferFailed` | 记录事件带来的下载单元和目标为“待复核”；事件只优化增量，不能倒放旧历史。 |

### 明确做不到：必须如实降级

1. `storage/list` 没有 inode 或硬链接计数。它只能证明目标文件当前存在，不能从接口层证明“这一个目标与那个源文件确实共享 inode”。本项目既有约束是媒体库文件都是硬链接；本插件可据此核验**目标是否存在及其结构是否正确**，不能把它说成底层硬链接取证。
2. 文件管理器里的手工删除、移动、改名不会给插件发通用广播。因此无法做到“刚手改立刻知道”。可以在下一次轻量对账或用户点“刷新变化”时发现；周期复核是必需的，不是可选优化。
3. 一个名称、目录和文件大小不足以绝对证明作品身份。原生识别和模型都可能不知道或猜错；身份无法被原生候选和官方预览共同支撑时，必须显示“无法确认”，不能自动整理。
4. 本机参考树里有一个未合并到上游 `v3` 的 `app.sdk.governance` 原型；上游相同路径为 404。它不能作为 NAS 已有能力或本 PR 前提。本 PR 只依赖实际发布 V3 的公开 REST、插件生命周期、事件和数据合同；若未来需要新的宿主能力，单独立项，不能夹带进本插件 PR。

## 地图是什么：保存什么、保存在哪里

地图不是把视频复制一份，更不是把媒体内容交给 AI。它是一个可增量更新的清单，保存于插件自己的 NAS 持久数据中。每条原始路径仅保留在运行时私有存储，用于再次调用官方接口；页面、日志、导出和报告只显示脱敏名称、类别和短指纹。

本 PR 先用插件私有 `media_map.json` 保存有界地图：下载单元、媒体库节点、历史摘要和 findings；每条都有 `schema_version`、扫描时间、集合指纹和来源。少量 salt、模型缓存和脏项使用基类 `save_data()`。路径相关索引使用每个插件实例私有 salt 的 HMAC；需要操作时从私有记录取原始 `FileItem`，不把路径作为 UI ID、日志 ID 或 Git fixture。数据量或查询需求真正超过该边界时，再以独立 PR 迁移到插件自有表，不能把 ORM 依赖夹进本次发布。

## 第一次建立地图：慢，但必须真做

用户点击“建立媒体地图”后，页面显示阶段、已完成目录/总目录、已发现下载单元、已核对媒体库结果、跳过/失败数和可暂停/继续状态。没有完成的根会明确标为“未覆盖”，绝不显示成“没有问题”。

顺序如下：

1. 读取当前下载根和媒体库根；保存其配置指纹。用户可在开始前看到本次会覆盖的“电影 / 电视剧 / 动漫”等配置名称。
2. 对每个下载根做有界广度优先遍历。顶层直接文件是一条下载单元；顶层直接目录是一条下载单元。不会用相似名字把相邻文件硬凑成一个“包”。
3. 对每个下载单元生成文件集合：视频、字幕、NFO、目录树、大小、修改时间、清洗后的季集线索和集合指纹。样片、预告、校验文件等单独标记，不能当正片。
4. 对每个媒体库根也建立同样的目录树和文件指纹。先建立当前实际结果，不从成功历史反推结果。
5. 分页读完成功和失败整理历史。以历史中的源、目标、下载 hash、`mode`、媒体身份做辅助关联；既不把失败次数当问题数，也不把成功记录当正确证明。
6. 先用确定性规则把源、目标、历史组成候选关系，再把无法决定的作品单元放入 AI 队列。规则通过的正常项不调用 AI。
7. 对已确认身份的候选逐一请求官方预览。以预览输出和当前媒体库结果比较，形成最终 finding；无法预览的项是“待核实”，不是“已正确”。
8. 写入地图版本和覆盖回执。只有所有已选根成功读完，才标记“基线完成”。

首次慢的原因是实际目录逐层读取，不是向 AI 塞了全库。读目录会并发但设上限，并对每个根分批；每完成一批立即落盘，因此重启后只补未完成分支，不从头再跑。

## 以后怎么快：事件优先，定期对账兜底

### 新下载或原生整理成功/失败

`TransferComplete` / `TransferFailed` 到来时，插件只做两件廉价工作：保存事件中的来源、历史 ID、下载 hash、目标线索和幂等键；把相关下载单元及目标目录标为 dirty。短时间内同一下载单元的多文件事件合并为一项，延迟到安静窗口结束再读取一次完整文件集合。

### 人工删除、移动、改名

没有可订阅的文件管理器广播，所以采用两层检查：

- **轻量对账**：每次打开页面、每次定时任务或用户点“刷新变化”时，先列出地图已知的根和上层目录，比较条目、大小、修改时间和目录指纹；未变的分支不再递归。
- **轮换深度对账**：分批把各根重新递归一次，避免某些存储不可靠地更新目录修改时间。用户可一键启动“全量复核”；它仍可暂停、续跑。

发现删、移、改后，只使受影响下载单元和媒体库目录失效，再重新关联。它保证“下次对账一定检查到变化”，不承诺一个不存在的实时推送能力。

## 怎么判定真正的问题

地图只展示 finding，不展示所有正常文件。分类采用用户能看懂的原因：

- **原生整理失败**：当前原始视频仍在，当前媒体库找不到可核验结果；历史失败仅可补充失败原因。
- **目录分类错误**：官方预览应落入的库类别与当前结果不同，例如动漫被放到电视剧。
- **目录层级错误**：作品/季/集的目录结构与官方预览不同。
- **集数或集号错误**：源集合的集号与当前结果或官方预览不一致，包含缺集、重复集、错集。
- **作品身份错误**：当前媒体库关联的作品身份与由整包证据、原生识别和预览共同确认的身份冲突。
- **无法确认**：信息不足、来源读取失败、原生候选冲突或预览失败；它不是自动修复对象。
- **旧历史残留**：历史显示失败，但原始文件和目标都已不存在，或当前事实已被新的关系覆盖；隐藏在问题页之外，可在历史说明中查看。

特别处理整理方式：成功 `mode=move` 时原始文件不在并不代表错误；只有本项目当前硬链接整理约束下、且源/目标关系都已核验时，才把“源在而目标不在”归为未整理。

## AI 到底做什么，怎样省 token

AI 不扫全库、不看视频内容、不自动执行整理。它只处理确定性规则无法回答的两个问题：一个下载单元里有哪些作品单元；每个作品单元最像什么作品。

给 AI 的不是完整文件库，而是压缩后的“作品候选卡”：去重后的文件名、目录相对层级、视频/字幕/NFO 数量、大小桶、季集线索、历史身份（标为非事实）、当前目标类别和冲突摘要。原始路径、密钥、日志和无关文件不会发送。

队列按批次提交，例如每批少量作品候选且有严格的字符预算；共享规则只放一次。输出必须是带候选序号的 JSON：`abstain`、标题/原名/年份、电影或剧集、季集、置信度、支撑证据序号和冲突说明。回答不能引用候选卡之外的信息，也不能输出操作指令。

模型答案只是“待核验线索”。插件必须再调用 MoviePilot 原生识别，取得完整 `media_source + media_id`，随后跑官方逐文件预览。原生候选冲突、低置信度或预览不完整时，停止在人工选择页。这样既能整包判断，又不会把模型的猜测直接变成删文件或建硬链接。

当前 AI 识别增强的思路可借鉴：它在原生名称识别失败后把文本交给 LLM，再交回原生链路二次识别。但它的现有实现是旧 API/旧导入，且输入主要是单个标题；不能直接复用进 V3。新插件复用“原生优先、AI 兜底、二次识别”这个原则，不复用旧代码。V3 是否提供可供第三方任意提交结构化批量 prompt 的稳定 Agent 调用合同，官方主文档没有承诺；本 PR 的实现必须先写一个**无媒体写入的 AI 调用契约探针**。若当前 NAS 运行时没有该稳定入口，AI 队列保留为“等待可用智能助手”，不能绕过宿主私有 LLM 代码或私接账号。

## 用户界面和修复闭环

首页只有三件事：地图状态（是否完整、上次对账、变化数）、“建立/继续地图”、待处理问题计数。点击某问题进入两步页面。

第一步“确认作品”：左侧是原始下载单元的脱敏结构和证据；中间是原生/AI 给出的候选（含原名、年份、类型、季集、来源和冲突）；右侧是当前媒体库结果。用户选定候选后，插件必须取得原生完整身份；否则不能进入下一步。

第二步“查看重建预览”：并排显示当前结果和官方逐文件预览的应有结果，具体列出类别、目录、每集和附加文件。此时明确显示会清理的旧目标数量及来源：它们必须同时满足“来自本次命中的成功历史”“仍在当前配置的媒体库范围内”“已在预览前重新读取存在”。

只有用户按“确认按此预览重建”后，调用官方 `transfer/manual`。不直接调 `storage/delete`，不删除下载原文件，也不按名称批量删除。执行后立即重新读取这个下载单元和相关目标目录，只有新结果与预览一致才关闭 finding；否则显示实际失败原因并保持待处理。

## 一个 PR 的实现范围

1. **删掉错误入口**：废弃以失败历史/启用后事件索引作为扫描范围的 UI 口径；保留历史读取仅作关联。
2. **地图存储与迁移**：新增插件自有表、schema 迁移、私有路径保护、断点续跑、地图版本失效规则和数据保留/清理策略。
3. **盘点器**：实现根目录读取、分页/有界遍历、下载单元边界、目录指纹、初次全量和增量 dirty 队列；页面展示真实进度和未覆盖范围。
4. **关联与规则引擎**：实现源—历史—目标匹配、模式差异、作品拆分、上述七类 finding，包含“无法确认”而非强行归类。
5. **AI 队列适配器**：先完成宿主稳定调用探针与 mock 合同；只有探针通过才启用受预算控制的批量队列、结构化校验、缓存和 abstain。探针失败时功能降级但地图和规则核对仍可用。
6. **官方预览与受控重建**：把身份确认、`manual/history`、逐文件 preview、最终确认、官方 cleanup/rebuild、执行后复核做成不可跳过的状态机。
7. **产品界面**：地图状态、进度/暂停/继续、问题列表、两级预览、不可用原因、只显示问题。
8. **测试与验收**：脱敏 fixture 覆盖单文件、整季、合集、旧失败残留、成功但错类/错季/错集、move 历史、手工删改和中断续跑；本地运行纯逻辑与迁移测试、V3 构建/加载。冻结候选后在 NAS 按“首次地图 → 增量事件 → 手动改动后对账 → 预览 → 单项重建 → 再核验”验收。任何一步未通过不进入发布。

## 不在这个 PR 里做的事

- 不扫描或发送视频内容，不做 OCR/音频/画面识别。
- 不依赖未合并上游 SDK，也不为此提交 MoviePilot 核心 PR。
- 不改变下载器、PT、代理、原始目录或既有硬链接策略。
- 不自动执行删除或整理；每项修复都需要预览和最终确认。

## 这次为什么和过去不同

过去的实现从历史表出发，因此范围本身不真实；有时很快但什么也没查到，有时很慢却检查了不该检查的历史记录。新设计把“当前文件事实 → 关系 → 官方预览 → 问题”固定为唯一顺序。它牺牲一次首次盘点的时间，换来以后每次只核对变化部分，并且每一条问题都能回到实际源文件、当前目标和官方预览，而不是回到一个历史数字。
