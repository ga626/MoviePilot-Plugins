# MediaGovernor：停止试错后的产品重建路线

> 结论：当前 `v3.0.0` 不是“再调一两个筛选条件”就能变好的基础。应停止继续往它叠功能，先建立一套能证明正确与否的验收底座，再按小而完整的能力切片开发。本文只做调研和设计，不修改插件、NAS 或媒体。

## 先讲人话

你要的产品很简单：MoviePilot 正常整理；它没有整理好，或看似整理好但放错作品、目录、季集时，MediaGovernor 找到**真正的问题**，让你先看清“现在是什么、应该是什么”，确认后由 MoviePilot 重建硬链接。

这两天没有做到，不是需求不清楚，而是开发顺序错了：每次都把“扫描范围、怎么把文件归成一部作品、AI 判断、界面展示、修复”一起改；没有一组公认答案来判断这版到底对不对。结果就是改严了漏检，改松了误报；每次安装都成了第一次真正测试。

**真正的保证不是承诺 AI 永远不猜错，而是让软件不再把猜测当结果。** 每个版本必须先在已知答案的样本上证明：该报的一条不漏、不该报的一条不报；再拿同一套样本和冻结的只读清单去 NAS 验证。做不到就不能发下一版。

## 已查明：当前版本为何会“0 个问题”

这是代码事实，不是推测。

1. 当前扫描先读下载目录、媒体库和成功/失败历史；但“是否算问题”仍由非常窄的规则决定。它仅直接报：纯失败历史、成功目标不存在、同一下载单元出现重复集号。已存在目标但作品错、目录错、季集错，一般不会先进入问题队列。
2. AI 被放在最后：只有先被上述规则打成异常的单元才会被发送给 AI。因此“表面成功但实际放错”的项目，AI 根本没机会看见。
3. 一个顶层下载目录被当作一个“下载单元”。同一个包内只要有一条成功历史，就可能遮住其中另一部分失败的文件；它也没有可靠地切成“这一部电影 / 这一季剧 / 这个合集里的多部作品”。
4. 当前测试主要验证“我们写的规则会返回我们写的结果”，而不是用真实已知案例证明它能发现错误。比如成功记录有目标时被断言为零问题，正好掩盖了用户最关心的“目标存在但整理错”。
5. 页面把“本轮未形成 finding”写成“发现 0 个真实待处理问题”。它没有先证明地图覆盖完整、身份链可用、官方预览已比较；所以这个 `0` 不能解释为“库里没有问题”。

换句话说，当前版本并不是“已经检查了所有内容且没有发现异常”，而是“在一套很窄的判断条件下没有形成卡片”。两者完全不同。

## 别人为什么不会这样做

成熟媒体整理工具的共同点不是更大胆地自动化，而是把四件事拆开。

1. **先建立可机器核验的结构。** Jellyfin 官方要求剧集按“作品目录 → 季目录 → 集文件”组织，并明确说作品名、年份和元数据 ID 能提高匹配可靠性。[Jellyfin TV Shows 文档](https://jellyfin.org/docs/general/server/media/shows/)
2. **自动匹配不能确认时给人工匹配，而不是伪造正确。** FileBot 的公开说明把缺失季集信息的情形转为 Manual Matching，可调整文件与集的对应、逐项 Edit Match。[FileBot 说明](https://www.filebot.net/forums/viewtopic.php?t=13909)
3. **执行前先预览。** Sonarr 的官方社区说明中，重新命名有 Preview Rename；需要时再手动导入，而不是把一次自动导入当永久正确。[Sonarr 说明](https://forums.sonarr.tv/t/sonarr-renaming-files-on-import/33206)
4. **发布前先缩小风险面。** Google SRE 对 canary 的原则是：先在一小部分真实流量验证，再扩大，而不是全量上线后才判断。[Google SRE Canary Release](https://sre.google/workbook/canarying-releases/)

中文实际使用经验也是同一件事：公开抖音检索能看到“先整理杂乱名称、再提高 Jellyfin/影视墙展示成功率”的实践；B 站也有用批量重命名提高刮削准确度的演示。它们说明“命名和结构是匹配基础”，**不**证明任何工具可以百分之百自动猜出所有乱包。抖音详情页受到平台访问限制，因此这里只把它作为弱的用户体验线索，不用它支撑技术结论。

## 产品应该怎样运转

### 1. 一张事实地图，不是一个失败历史数字

首次运行建立两张清单：

- 下载区：每个顶层下载包、里面所有视频/字幕/NFO、相对层级、大小/时间摘要、可解析季集线索。
- 媒体库：现存文件的同类清单，以及每条成功历史指向的目标线索。

历史失败只是一条线索，不能决定数量；成功历史也不是“正确证明”。地图完成必须给覆盖回执：读了哪些根、多少下载包、多少媒体项目、哪些根读失败或未覆盖。没有覆盖回执，页面只能显示“未知”，不能显示“没有问题”。

### 2. 全部文件都参与，但 AI 不必吞掉全部文本

“全部交给 AI”这个方向的一半是对的：系统必须先看完整结构，不能先用失败历史框死范围；但把全库原始文件名一次塞给 AI，会慢、贵、且无法稳定复现。

正确方式是两层：

- 程序对**全部**下载包建立结构化地图，做无争议的切分、去重、关联和变化检测；规则只负责压缩、索引和找冲突，**不负责宣布正常**。
- 每个仍无法确认的“作品单元”把整包的压缩证据卡批量交给 AI：去重文件名、层级、集号、字幕/NFO 数量、大小桶、现有历史/目标冲突。AI 可以一次看到同一包的完整关系，却不需要每次重读无关的正常库。

AI 的输出只能是“候选身份和理由 / 不确定”。随后必须由 MoviePilot 原生识别得到可用身份，再由官方预览算出逐文件应有位置。AI 不能直接决定删除或重建。

### 3. 用“当前结果”与“官方应有结果”比，而不是用名字比名字

对于身份已确认的作品单元，调用官方预览取得它会怎样整理每个文件。再和媒体库当前事实做逐文件对比，才可以分成：

- 原生整理失败：原始视频仍在，且没有可核验的当前目标。
- 目录分类错误：电影、剧集、动漫等落在错误类别。
- 目录层级错误：作品/季的目录不对。
- 集数或集号错误：漏集、重复、错集或一集对应错文件。
- 作品身份错误：当前结果的身份和经过核验的身份冲突。
- 无法确认：信息不足、候选冲突或官方预览失败；它不能被自动修复。

这正好覆盖你说的两大类：根本没整理成功，以及看起来成功但里面错了。

### 4. 修复是一个独立的、受控的产品能力

一条问题卡点开后必须有两步：

1. 确认作品：看原始包结构、候选的中文名/原名/年份/类型/季集、当前媒体库结果；必要时选候选。
2. 官方预览：左边当前硬链接结果，右边官方逐文件预览，明确列出会替换的旧目标。

只有最终确认才调用 MoviePilot 官方整理路径来处理本次确认的旧目标并重建。插件不直接删原文件，也不按名称扫删硬链接。执行后再读取当前结果；与预览不一致就保留问题卡。

## 可实现边界

MoviePilot 现有公开页面接口足以做“目录事实、整理历史、原生候选、官方预览和官方执行”的闭环；但有两个边界必须先承认：

- 目录列表没有 inode/硬链接计数，所以插件能证明“目标存在、位置是否符合预览”，不能从接口证明两个文件底层一定共享 inode。
- 文件管理器的手动删改没有通用插件广播。解决方法是事件标脏加定期轻量对账；不能假装实时知道。

此外，AI 批量调用在当前宿主中的稳定调用合同必须先用**零媒体写入的契约探针**验证。探针不通，身份不确定项应显示“智能助手不可用”，不能用私有接口、猜接口或直接接管用户账号绕过去。

## 不再绕圈的开发流程

### PR 0：先做“判卷机”，不碰 NAS 媒体

建立脱敏金标准样本。每个样本都必须写清：原始下载树、当前媒体库树、相关历史摘要、正确作品身份、官方预览应有树、预期分类。至少包含：真正失败、成功但错分类、错季、错集、动画与真人版同名冲突、一个包部分成功部分失败、旧失败历史但实际已恢复、手工删改后目标缺失、正常样本。

验收条件：任何新算法先跑这套样本；已知问题 100% 找到，正常样本 0 误报，且每条输出都能说明证据来源。没有这套“判卷机”，禁止再发布检测逻辑。

### PR 1：只做完整地图和覆盖回执

只实现读取、分包、根去重、断点续跑、增量指纹、覆盖状态和进度；不接 AI、不修复、不发布“发现了什么”的结论。

验收条件：固定 fixture 与只读 NAS 验收都能显示“覆盖多少 / 未覆盖多少 / 为什么”，地图状态能在刷新后正确回显；`0` 永远不是覆盖不足的别名。

### PR 2：只做作品单元和身份候选

对所有作品单元走“确定性解析 → 原生识别 → 对不确定/冲突单元批量 AI → 原生二次核验”。加入候选页和 `无法确认` 状态；仍不执行整理。

验收条件：同名动画/真人版、合集、部分成功包等金标准样本都返回正确候选或明确弃权，绝不产生一批一模一样的假候选。

### PR 3：只做整理正确的只读审计

对已确认身份的样本请求官方预览，做“当前树 vs 预览树”的逐文件差异；只展示真正问题，不把正常文件塞给你审。

验收条件：上述五类错误均被样本命中；正常样本不出现；官方预览失败则标为未知，不能关闭问题或自动修复。

### PR 4：最后才做单项受控重建

对一条已确认问题生成预览、冻结预览、最终确认、调用官方重建、执行后复核和回执。先用一个可回滚的脱敏/测试项做真实宿主验证，再进入发布。

验收条件：原文件不被插件直接删除；只处理预览清单中能证明属于本次项目的旧媒体库目标；重建后实际树等于预览树；失败可以解释且不会扩大影响。

## 每次开发必须遵守的止损线

1. 一个 PR 只能改变一层：地图、身份、审计或修复，不能四层一起改。
2. 先跑金标准样本，后做一次冻结的 NAS 只读/最小写入验证；不能把用户安装当测试。
3. 任何“0 个问题”必须同时显示覆盖已完成、身份链可用、预览比较已完成的数量；否则叫“尚无结论”。
4. 新样本一旦暴露错误，先加入金标准，再修代码；不能只针对当前界面临时调阈值。
5. 发布只提升已经过相同验收的候选；若 NAS 验证发现合同缺陷，立即停止收口，回到新候选，不在同一安装代际里补丁式试错。

## 最终判断

现在不该继续把 `v3.0.0` 的筛选阈值从宽调窄或从窄调宽。它的根问题是：没有一个能对“真实问题”判卷的底座，且把 AI、规则和修复顺序放反了。

能把功能做出来，但顺序必须改成：**先可验证的样本 → 全库事实地图 → 身份核验 → 官方预览差异 → 单项受控修复**。PR 0 是唯一正确的下一步；它不产生可安装的新功能，却会第一次让我们在发版前知道“这版究竟有没有把你关心的问题找出来”。
