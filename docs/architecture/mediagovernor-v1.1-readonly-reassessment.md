# MediaGovernor v1.1 只读复盘与重构计划

日期：2026-09-03。范围：已安装的 `MediaGovernor v1.0.1`、本地 V3 源码、MoviePilot V3 公开合同、已启用的 AI识别增强插件与公开资料。本文只说明问题和方案；不改插件、NAS 配置、媒体、下载或硬链接。

## 先说结论

这 47 条不是“文件里没有作品信息”的证明，而是当前插件几乎没有使用那些信息。它逐条拿失败历史中的**一条来源路径**让 MoviePilot 识别；拿不到唯一身份就停止。所谓“整包检测”只在已经识别成功后，递归数一数视频和字幕数量，既不把文件名交给识别器，也不拿来反证识别结果。因此：

- 检查慢、没有进度，是当前前端串行跑完所有请求后才一次性更新结果；
- 多数记录找不到，是单路径、单来源链路失败后没有整包回退；
- 《星际牛仔》动画被当成 2021 真人版，是“有任何身份就当成功”，没有拿 26 集文件集合、年份、类型和候选详情做交叉校验；
- 你要求的第二个功能“整理正确”目前确实没有实现。现有按钮只会为已选身份生成一次新硬链接预览；它不检查旧链接是否错、不比较季集/分类、不展示删除范围，也不会受控重整旧目标。

所以 v1.1 不能继续在现有页面上加几个按钮；应重做为两个独立工作台：**找对作品**和**整理正确**。AI 是前者的一个受约束步骤，不是把文件夹名随便扔给模型后自动写盘。

## 现场事实与根因

### 1. 为什么慢且没有进度

`plugins.v3/mediagovernor/src/components/AppPage.vue` 的 `inspect()` 先一次取完失败历史，再以 `for ... await packageFor(row)` 串行处理。每条都会请求 `media/recognize_file`；识别成功后还可能逐目录串行调用 `storage/list`，上限为 120 个目录、6 层。页面只有“检查中…”这一个布尔状态，没有已完成数、当前阶段、耗时、可暂停或逐项结果。

这不是 NAS 变慢的证据，而是客户端把 47 条远程识别和目录读取排成一条队列。单条卡住时，用户看不到任何可验证的进展。

### 2. 为什么 47 条只得到一个“答案”

当前 `packageFor()` 的顺序是：

1. 从失败历史取 `src_fileitem.path`；
2. 调 `GET /media/recognize_file?path=...`；
3. 只要返回 title、source、id、type 四项，就认定“已识别”；否则立即标记“没有可靠作品身份”；
4. 只有第 3 步成功后，才读取来源包，并且只返回视频/字幕/目录的**数量**。

也就是说，46 个未识别包的文件名、父目录名、集号模式、字幕名、NFO 是否存在、同包文件是否互相指向同一作品，都没有参与判断。当前“找作品”按钮也只用 `source.name` 做一次 `media/search`，只取 3 条候选；没有别名、年份、类型、集数或数据源比较。

MoviePilot 的公开文档还明确：影视自动识别在未指定来源时只走默认 TMDB，未命中不会跨数据源继续兜底。当前插件没有取得已启用数据源列表，也没有发起多来源、候选详情或集数核验。因此高失败率是设计限制，并不能推出这些媒体本身不可识别。

### 3. AI识别增强实际能做什么、不能做什么

AI识别增强是 MoviePilot 原生 `NameRecognize` 的辅助识别器：它把标题（可带路径时也可解析路径）交给当前 MoviePilot LLM，返回标题/年份/类型/季集，再让 MoviePilot 二次匹配；低置信度样本可沉淀为 `CustomIdentifiers` 建议。它不是视频内容识别器，不会读取视频画面、音轨或字幕正文。

当前 MediaGovernor 没有调用它的公开工作清单/复查接口，也没有把“整包文件清单 + 多个候选”交给它。通过原生 `recognize_file` 时，宿主可以按自身识别顺序触发 `NameRecognize`，但该辅助事件只携带当前标题，不携带整包证据；AI插件默认还会把“仅标题”失败样本排除在沉淀之外。故它最多是一次单标题修正，不能解决本次 47 条的整包还原问题。

### 4. 《星际牛仔》为什么会错

画面显示该卡片归集了 3 条失败历史，来源包有 26 个视频和 26 个字幕，却直接显示“星际牛仔真人版（2021）”。现有逻辑只要 `recognize_file` 返回了一个身份，就跳过候选对比；随后统计出的“26”也没有用于校验。它没有问：候选类型、年份、候选的季/集结构、同包文件名和原始/别名是否同时支持这个答案。

v1.1 必须把这种情况列为“**冲突，禁止预览**”，而不是“可整理”。候选详情、文件集的季集范围和至少两个独立名称线索不能同时支持时，必须显示动画版与真人版等候选及冲突原因，等用户选择；不能由热度排序或 LLM 自信度替代。

### 5. “整理正确”现在缺在哪里

现有 `manualPayload()` 固定 `transfer_type='link'`、`reorganize=false`，不带 `logid`；`repair()` 只调用一次 `POST /transfer/manual`。它没有调用：

- `POST /transfer/manual/history`：查某来源/目录命中过哪些成功整理历史；
- `POST /transfer/manual/target-path`：查当前目录规则会把它送去哪；
- 带 `logid` 与 `reorganize=true` 的官方手动整理：这是宿主处理“旧成功历史和非移动旧目标”的受控重整入口。

MoviePilot 的公开合同说明，`reorganize=true` 会清理命中的成功历史及非移动模式旧目标。因此插件绝不能自行删除文件，也不能把“创建新链接”冒充“修正旧链接”。正确做法是：先用官方零写入预览列出来源、旧目标、拟删除旧链接、拟创建新链接及季集变化；用户逐包确认后，才调用官方重整入口。若旧记录是移动/复制、目标不可读、身份冲突或预览不完整，则禁止自动执行。

## v1.1 产品方案

### A. 找对作品工作台（只读直到用户确认）

每个来源包依次产生以下证据，不把真实路径持久化或展示在报告中：

1. **包清单**：父目录名、有限数量的视频/字幕/NFO 文件名、文件扩展名、目录层级、集数模式、视频/字幕数；先浅后深，达到足够证据即停止。
2. **确定性清洗**：去掉分辨率、编码、发布组、语言、站点标签等噪音，提取可能的标题、年份、SxxExx/范围、季度和版本词。
3. **多线原生识别**：对目录名和少量有代表性的首/中/末视频名分别调用 MoviePilot；先从 `GET /media/source` 发现当前可用来源，再按来源检索，不写死某个动漫库。
4. **候选核验**：取得候选详情，比较标题/原名/年份/类型、季集范围、文件集数量和重复命名一致性。不是“搜到就算”，而是“多条证据是否同意”。
5. **可选 AI 仲裁**：只在确定性步骤得到少量互相冲突的候选时使用。输入为脱敏文件清单摘要、已解析的季集和候选卡，不给模型写盘权限；输出必须包含支持理由、反证与“无法确定”。AI 结果只能排序或建议，不能直接成为执行身份。

状态只分四类：`已确认`（可预览）、`待你选择`（候选冲突）、`资料不足`（没有可读视频/有效名称）、`来源不可用`（文件已不存在或无权读取）。后两类才是真正需要人工补信息或无法处理的情况。

与 AI识别增强的关系：保留它做日常原生整理的单标题兜底和失败样本治理；v1.1 通过版本/健康检查后可把它作为**可选适配器**用于标题归一化或复查，缺失、超时或返回低置信度时自动退回原生链路。不得把对另一个第三方插件的私有实现当硬依赖，也不得自动写 `CustomIdentifiers`。

### B. 整理正确工作台（先审计，再预演，再确认）

它不从“失败记录”局限出发，而是审计所有被选中的整理历史：

1. 找对作品工作台先给出已确认的身份；历史中已有身份的项目也进入一致性检查。
2. 读取官方历史摘要和当前目标规则，显示“现在在哪、按当前规则应去哪、为什么认为不对”：类型目录错误、季目录错误、集号冲突/缺集、同包落到多个作品、旧目标不存在或链接策略不一致。
3. 对每个包调用官方 `preview=true` 生成逐文件方案。验收条件是：所有视频都有目标、没有重复目标、季集连续性与候选详情不矛盾、字幕能与视频配对、目标目录符合当前规则。
4. 仅当预览完整且旧目标可明确归因为成功的硬链接整理时，显示“重整此包”确认框。框内明确列出旧链接数量、将删除的目标数量、将新建的链接数量、不会触及的来源文件。
5. 用户确认后才调用 MoviePilot 官方 `reorganize=true`；执行后重新只读核验历史与目标摘要。任何一步变更、超时、目录规则变动或源包指纹变化，都作废旧方案并要求重新预演。

这才满足“清掉错误硬链接，再恢复一套正确硬链接”。删除权始终在 MoviePilot 官方重整能力，不在插件自己的文件操作里。

### C. 体验与速度

“开始检查”改为可恢复的批次任务，而非一次性黑盒：

- 顶部固定显示阶段、`已完成/总数`、已确认/待选择/资料不足/来源不可用数量、当前包和耗时；首条历史读取成功后立即出现，不等 47 条结束。
- 任务按小并发队列运行（初始上限 2--3，并根据 MoviePilot 响应自动降速），每处理一包就渲染一个可解释卡片；不再 47 条串行等待。
- 支持暂停、继续、停止后保留已完成结果；停止只是不再派发下一包，不中断正在进行的宿主请求。
- 对同一历史 ID + 来源包指纹缓存只读证据；路径、文件清单原文不写入浏览器长期存储。源包、目录规则或插件版本变化即失效重查。
- 两阶段取证：先目录名和少数代表文件快速给出结论；只有身份冲突、包结构异常或需要执行预览时才递归读取更深目录。这样把昂贵目录遍历留给真正需要的少数包。

## 实施顺序与验收

```mermaid
flowchart LR
  P0[P0 可见进度和只读分桶] --> P1[P1 包级识别与候选核验]
  P1 --> P2[P2 整理正确预览与受控重整]
  P2 --> P3[P3 NAS 候选验收和发布]
```

### P0：把问题看清楚（只读）

实现逐包进度、暂停/继续、失败原因分类和证据摘要；对当前 47 条跑一次，只产生报告。验收：页面一开始就有进度；每条都有“为什么没找到”；没有任何文件写入。

### P1：找对作品

实现包级取证、候选交叉验证、动画/真人版与翻拍冲突拦截、可选 AI 适配器和用户选择页。验收：用“26 集《星际牛仔》包”回归，真人版候选必须因证据冲突而不能直接进入预览；所有已确认卡都能展示支持与反对证据。

### P2：整理正确

接入公开历史查询、当前目标路径、逐文件官方预览和受控 `reorganize` 确认。验收：构造不改真实媒体的 fixture，覆盖分类错、季错、集错、缺集、旧目标不可读、移动历史和预览不完整；只有硬链接旧目标且预览完整的项目才能出现执行按钮。

### P3：真实环境候选验收与发布

冻结候选 ZIP 后，在 NAS 仅对一小组获明确授权的测试包跑 P0/P1 和零写入预览；真实重整只在你确认预览内容后执行。候选必须绑定源码 SHA、ZIP SHA、宿主版本和逐包回执。通过后才走 PR/CI/Release；不能把页面截图或单次成功当作全量验收。

## 详细执行步骤

本次交付**只改报告，不改代码**。以下是下一次获准实施时的执行计划；每一步的输入、动作、输出、验收与依赖均冻结在此，避免把修复、媒体写入和发布混在一起。

1. **P0 — 可见、可停的只读检查。**输入：失败和成功整理历史、公开历史/识别/存储接口。做什么：把现有串行循环改为小并发队列，每个来源包输出阶段和原因；怎么做：先读取历史总数，再按“历史读取→快速名称证据→需要时深层目录证据”更新进度，停止时不再派发新任务。输出：可暂停工作台和四类原因统计。验收：首个进度在首条历史返回后显示；暂停不发起新请求；全程零写入。依赖：无前置依赖；代码变更：是，仅插件前端和定向测试。
2. **P1 — 找对作品。**输入：P0 的脱敏包级证据、`media/source`、识别/搜索/详情结果和可选 AI 插件健康结果。做什么：得到可解释而非单点猜测的身份；怎么做：以目录名与代表文件名做多线原生识别，查询动态来源，拉候选详情，按标题/年份/类型/季集/文件集投票；只有冲突时调用可选 AI 适配器。输出：已确认、待选择、资料不足、来源不可用四类卡片和候选证据。验收：26 集《星际牛仔》动画包不能因真人版单个匹配直接变成可预览；候选冲突时没有执行按钮。依赖：P0 已能产生稳定包证据；代码变更：是，插件前端、适配层和 fixture。
3. **P2 — 整理正确。**输入：P1 已确认身份、整理历史、当前目录规则和官方预览。做什么：发现并纠正错误分类/季集/旧硬链接；怎么做：先查命中历史和目标路径，再用官方 `preview=true` 得到逐文件目标，完整核验后才暴露一次 `reorganize=true` 确认。输出：按包显示的旧目标/新目标/删除数量/创建数量/风险说明和执行回执。验收：移动/复制/目标不可读/预览不完整的包不可执行；合格硬链接包只能由官方重整入口删除旧目标。依赖：P1 身份已确认和 P0 指纹未变；代码变更：是，插件界面、合同测试和脱敏 fixture。
4. **P3 — 候选与发布。**输入：冻结源码 SHA、同一 ZIP、P0--P2 自动测试和你批准的最小 NAS 测试包。做什么：真实验证后发布；怎么做：先在 NAS 做只读和零写入预览，再由你确认任何真实重整，之后按 PR/CI/main/Release 收口。输出：不可变 Release、远端 SHA 和逐包回执。验收：Release ZIP 与候选 SHA 一致；未获得你对预览的确认绝不写媒体。依赖：P0--P2 定向验证通过；代码变更：否（此阶段只验证和发布）。

## 当前不能下的结论

尚不能逐条断言那 46 个包分别是文件缺失、目录层级错、命名脏、跨版本混包还是 AI/数据源问题：当前页面没有采集或显示这些证据。P0 的目的正是先把这 46 条分桶。可以确定的是，它们还没有经历本报告设计的“整包证据 + 多候选核验”流程，故现在把它们归为“无解”是不成立的。

## 技术边界

本地曾存在一个未上游化的 `app/chain/transfer/governance.py` 原型；与已 fetch 的 MoviePilot 官方 `v3` 分支对照，该文件在官方当前分支并不存在。v1.1 不依赖它，不走私有数据库/文件系统，不要求为此先向官方提交 PR。首版只使用已公开的 MoviePilot REST 合同：媒体来源/搜索/详情/识别、存储列表、整理历史、目标路径、手动预览与手动重整。若后续发现这些公开接口不足以完成安全闭环，再单独提出上游扩展方案，不在插件中猜测或绕过。
