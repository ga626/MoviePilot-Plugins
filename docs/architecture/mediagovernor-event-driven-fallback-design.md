# MediaGovernor：原生整理后的最终兜底方案（单 PR）

日期：2026-09-04。本文只更新设计与实施清单：没有改插件、NAS、媒体、下载或硬链接。

## 先说结论

这个插件只做第二道保险：MoviePilot 先正常整理；MediaGovernor 再找出两种真正有问题的情况，并让用户在预览后一次确认修好。

```text
原生整理
├─ 失败：找对作品 → 预览 → 从原文件建立正确硬链接
└─ 成功：核对实际结果和应有结果
          ├─ 一样：不打扰
          └─ 不一样：删错的媒体库硬链接 → 从原文件建立正确硬链接
```

这里的“删”只删媒体库里本次已经核实的旧目标；不删下载原文件。这个结论依赖用户已经建立并持续遵守的库规则：媒体库（动漫、电影、电视剧等）之外的原始目录保存原文件，媒体库里的这些整理结果都是硬链接。插件仍会在执行前验证每个删除目标确实在当前配置的**媒体库目录**内；不在就拒绝执行。

## 1. 页面只显示人能看懂的原因

不再使用“待恢复”“现状与应有状态矛盾”之类名称。问题卡只会落入以下一类，并显示具体原因：

| 分组 | 显示的原因 | 何时成立 |
| --- | --- | --- |
| 原生整理失败 | 原生返回的失败原因；或没有生成目标 | 有当前失败事实，且来源包仍可读取 |
| 目录分类错误 | 例如动漫被放到电视剧/电影，或目标类别不是官方预览给出的类别 | 已确认身份，现有目标类别与官方预览不一致 |
| 目录层级错误 | 作品、季或规定的目录层级不对 | 官方逐文件预览与现有目标的层级不一致 |
| 季集错误 | 集号错、重复、漏到另一季或目标文件对应错 | 同一来源—目标逐项对不上 |
| 文件不完整 | 本次来源包应整理的文件没有对应目标，或一个目标对应多个来源 | 有逐项映射证据；不把“用户只下了部分集”误判为错误 |
| 手动改动 | 用户在文件管理器删除、移动或改名，原记录已不能代表现状 | 只关闭/刷新记录，不自动重新入库 |
| 无法判断 | 空包、不可读、没有可区分线索、模型放弃或预览不完整 | 没有足够事实，不猜 |

“原生整理失败”只写失败原因，不假装已经知道如何恢复。所有其他分类也必须有“当前目标”和“官方预览”两边的具体差异，不能只凭历史上失败过、目录名字像什么或缺集报警。

## 2. 不是逐个让 AI 猜，而是先全量整理证据、再分批判断

用户的思路成立，但“把整个媒体库一股脑塞进一次模型请求”不可行：一次超长输入会截断、变慢，并让模型把几部同名作品混成一部。正确实现是：**先把所有包都用同一套规则筛完，再把需要判断的包作为一个批次队列送给 AI；队列超过输入上限才切页。**

1. 首次建立索引时，读取已配置的下载目录和媒体库目录，去掉重叠根目录，按下载包而不是“一个含视频的父文件夹”分组。每包生成一张证据单：目录关系、文件名、视频/字幕/NFO 数、年份/季集线索、当前来源和目标摘要。
2. 先完成全量确定性筛选：无视频、样片、重复根、已有可靠且完全一致的结果直接结束；其余包才进入“需要 AI 判断”队列。页面先显示扫描总数、去重数、跳过原因、待 AI 数和覆盖范围，不能预设 47 或任何历史数字。
3. 对待 AI 队列生成一个共享规则头和多条压缩包摘要。每个包都有匿名 `package_id`；模型必须按 `package_id` 分别返回身份、证据索引、置信度与放弃理由，不能自行把两个包合并。达到固定 token/条数上限时按页切分，但同一次扫描的所有页都使用同一规则版本与快照。
4. AI 只提出假设。每个假设仍要用 MoviePilot 已启用的数据源搜索和详情核验中文名、原名、年份、类型、季/总集；动画/真人版、翻拍、年份或季集冲突一律进入“选择作品”，不自动修复。

这样节省的是重复规则、重复标题和重复调用；不是少看文件，更不是让 AI 代替事实核对。缓存键为“包指纹 + 规则版本 + 模型版本 + 数据源版本”，包未变化不再付费。模型输入和持久化状态都不存真实根路径；预览时才从 MoviePilot 当前数据重新读取必要的文件项。

## 3. 事件、旧记录和手工文件管理如何一起工作

### 新发生的整理

`TransferComplete` / `TransferFailed` 只会在插件已启用后的整理结算时产生，而且是按主视频文件发送，不是“历史库自动重播”。插件通过 V3 `app.sdk.events` 接收事件，以 `idempotency_key`/历史 ID 去重；相同来源父包在短暂静默窗口内合并，窗口结束后再读取完整文件树，形成一张包级证据单。不会每来一个视频就调用一次 AI。

### 已经存在的整理

安装或手动点击“建立索引”时，才做一次受限的初始回填：先读当前目录，再读成功/失败历史来补来源—目标关系。历史只帮助找到关系，**不等于问题清单**。索引结束必须显示“实际读取到多少包、未读多少、为什么未读”；以后不再用“历史失败 47 条”冒充问题总数。

### 用户在文件管理器手动删、移、改名

文件管理页的删除操作没有通用的“通知所有插件”事件，所以不能假装即时知道。解决办法是轻量对账，而不是重新全库跑 AI：

- 每次打开工作台、每次事件包完成、以及低频定时服务，只重新检查已建证据单的目标父目录和指纹；首次索引之外不扫无关目录。
- 目标不见了且原文件仍在，标记“手动删除，已从待处理列表移除”，不自动重新建立，因为这可能正是用户不想看的电影。
- 目标被移动/改名、源包或目录规则改变，旧预览作废并要求重新预览；不会根据旧路径删除或重建。
- 新增但没有整理事件的文件，由用户点击“建立索引”或低频受限补偿窗口发现；补偿同样先规则筛选、再批量 AI，不逐条调用。

## 4. 修复时到底怎么删、怎么重新建

文件管理页确实有 `POST /storage/delete`，它能删除传入的 `FileItem`。但本插件不应直接把它当成“删完再另起一次整理”：删后若历史还在，原生去重可能阻止重建。`reorganize=true` 的清理范围更宽，当前目标是只修复本次已核实的一条旧目标，因此不用它来猜测或扩大删除范围。

正确做法是复用 MoviePilot 同一个官方手动整理入口：带本次成功历史的 `logid`，使用确认后的身份、`transfer_type=link`、`reorganize=false` 执行。当前 V3 实现会以原始来源为输入，把该历史的 `dest_fileitem` 放入冻结的 `cleanup_dest_fileitem`，由宿主在同一整理计划里**先删除旧目标，再建立新硬链接**。底层清理仍走和文件管理按钮相同的统一删除能力。这正好完成你要的事，同时不会碰原文件。

执行按钮只能在以下全部通过后出现：

1. 本次预览仍新鲜：来源包、身份、目录规则、目标指纹均未变化；
2. 每一个拟删除项目都来自本次成功历史的 `dest_fileitem`，并且在 `storage/directories?directory_type=library` 返回的具体媒体库范围内；页面显示其实际类别标签，例如“动漫 / 电影 / 电视剧”，不使用一个泛泛的根目录；
3. 每一个来源文件都仍在当前下载目录；任何删除列表里出现来源文件、下载目录外项目或无法读出的项目，整包锁定；
4. 官方 `preview=true` 返回完整逐文件新计划，且没有身份、类别、季集、重复映射或目标唯一性问题；
5. 用户在三列预览（来源 / 当前媒体库目标 / 新目标）确认一次。执行回执逐项显示“旧链接已删、已建新链接、失败原因”；删除成功但新建失败则保留“重建失败”卡，原文件还在，可重新预览后重试。

因此插件不会通过裸文件系统命令删东西，也不会删除整个动漫/电影目录，更不会在用户手工删片后自己补回。

## 5. 单 PR 的完整实施内容

这是一份 PR，但内部按下列顺序完成；前一项的 fixture 和测试不通过，后续不接真实宿主。

| 顺序 | 修改位置 | 要实现的内容 | 完成标准 |
| --- | --- | --- | --- |
| 1 | `src/lib/governance.js` | 提取纯规则：包边界、去重、证据单、批次分页、状态分类、预览差异、目标范围校验 | 固定样例能稳定得出上述七类结果；正常/部分下载不误报 |
| 2 | `__init__.py` | 用 `app.sdk.events` 接收完成/失败事件；持久化脱敏包索引、队列、包指纹、规则/模型版本；新增有边界的批量 AI 接口 | 重复事件只产生一包；停用前历史不被伪称为事件；模型只收到脱敏摘要 |
| 3 | `AppPage.vue` | 改为“建立索引 → 规则筛选 → 批量判断 → 结果”进度；显示实际数量和未覆盖原因；增加原生失败、整理错误、手动改动三个列表 | 全程有进度、可暂停/继续；无问题包不出现在修复列表 |
| 4 | `AppPage.vue` 与后端受控 API | 身份选择页、三列预览页和修复确认页；动态读取当前 `storage/directories`，把目标显示为动漫/电影/电视剧等实际分类 | 动画/真人版、翻拍、错季、错类必须锁定或让用户选；预览不完整没有执行按钮 |
| 5 | 后端受控 API | 冻结执行前复核来源、目标、目录配置和预览指纹；只调用官方 `transfer/manual` 的 `logid + link + reorganize=false` 路径；写脱敏执行回执 | 任一范围越界/状态变化即拒绝；只会由宿主清旧目标并重建，绝不直接删除源文件 |
| 6 | fixtures、单元/组件测试、验收页 | 新增真实问题类型的脱敏样例和可打开的验收页 | 每个样例同时显示输入、预期、实际、差异和耗时；不读取 NAS、不调用真模型、不写文件 |
| 7 | 版本、文档、构建与候选 | 同步版本和用户说明；构建 ZIP、跑受影响测试和结构检查；冻结后做一次真实宿主验收 | 同一候选 ZIP 通过：加载、事件模拟/索引、批量 AI mock、预览、零风险执行样例；再按 PR/CI/main/Release 收口 |

### 必须覆盖的验收样例

- 原生失败但源包还在；历史失败但后来已整理好；
- 动画版与真人版《Cowboy Bebop》；同名翻拍；模型放弃；
- 动漫被放进电视剧、电影被放进动漫、季目录错误、集号错位、重复映射；
- 用户只下部分集（不报警）；样片/空包/不可读（不送修复）；
- 用户在文件管理器删掉媒体库目标（关闭记录，不自动补）；
- 旧目标在媒体库且来源在下载目录（允许修复）；任何反向/越界组合（拒绝）；
- 删除旧目标成功但新建失败（留下可重试回执，源文件不受影响）。

## 6. 做得到与做不到

| 目标 | 结论 |
| --- | --- |
| 先把所有文件按包整理成统一材料，再集中给 AI 判断 | 能做；采用“全量规则筛选后、按输入上限分页的批量 AI”，不是逐条 AI |
| 发现原生失败和表面成功但分类/层级/季集错的结果 | 能做；后者必须先确认身份，再与官方逐文件预览对照 |
| 自动删掉错误硬链接再重建 | 能做，但仅在本报告的五项执行前提成立时，交给 MoviePilot 同一手动整理计划完成 |
| 绝不删原始下载文件 | 本插件的删除清单只接受成功历史的媒体库 `dest_fileitem`；来源/下载目录/越界项直接拒绝 |
| 自动知道用户在文件管理器的一切改动 | 做不到即时广播；用轻量对账发现并关闭/作废旧记录，绝不自作主张补片 |
| 证明整个库永远没有问题 | 做不到；页面必须显示本次覆盖范围、上限和未覆盖原因 |

## 证据与调研边界

- 本机匹配 V3 源码证明：`/storage/delete` 是管理用户的文件管理删除入口；`/transfer/manual` 带成功历史 `logid` 且 `reorganize=false` 时，使用原始来源并挂入旧目标清理；执行计划会在转移前调用统一清理能力。
- 本机源码还证明：整理成功/失败事件包含文件、媒体、整理结果、下载上下文、历史 ID 和幂等键；它们只发生在当时的整理结算，不会重播旧历史。文件管理删除入口没有向所有插件广播的通用事件。
- 上游公开文档的检索结果与此一致：[`mcp-api.md`](https://github.com/jxxghp/MoviePilot/blob/v3/docs/mcp-api.md) 说明了 `manual/history`、`manual`、`preview` 及重整语义。GitHub 原文抽取对纯文本响应降级，故关键结论以本机匹配 V3 源码为准。
- 本轮没有读真实媒体、数据库、日志或 NAS 路径，也没有调用模型或执行删除。详细回执和主张链见同名 `.evidence.json`。
