# MediaGovernor 5.1.2：只读识别候选合同

日期：2026-11-02。类型：发布影响候选，当前仅第 1 步；不代表正式发布、NAS 安装或现场验收。

## 顺序与授权

用户明确要求先整理 11 月 2 日自动只读对账为干净、带版本号的可安装包，完成必要提交、CI、候选流程，再在 NAS 保持只读且 AI 关闭验证真实样本，最后按识别标准验收。本轮只完成第 1 步；不执行第 2 步的安装，不执行任何媒体修复，不新增产品能力。

这三步合理。唯一需要明确的验收语义是：“未证实关联”不等于“确定缺失”；源中本来未下载的集数与已下载但未关联的文件不能混淆；正常、缺失、错链与没查完必须按逐文件证据区分。既有助手结论只作样本线索，不是不可质疑的答案。

## 第 1 步完成条件

1. 任务运行源码、测试、版本合同和构建资源均已提交；构建包只从 Git HEAD 读取，不能从脏工作树打包。
2. 采用既有 `build_plugin_release_zip.py`；核对 ZIP 的每个成员与同一提交逐字节相同，结构、版本、默认安全配置、联邦入口和引用资源完整，记录源码 SHA 与包 SHA-256。
3. 本地仅跑插件受影响验证与一次完整候选回归；GitHub PR CI 必须真实执行，不能以本地结果顶替，也不绕保护、跳过或伪造状态。
4. 留下 PR/CI、源码、包、远端状态与未验项的独立回执。不在此文档预填自身提交 SHA；未推送/无 CI 时明确第 1 步尚未完成。

GitHub 操作必须按既有安全顺序：先推送任务分支，再创建 `MediaGovernor_v5.1.2` 私有 draft Release、上传冻结的同一 ZIP，回读 `isDraft=true`、未公开状态与远端资产哈希，再创建 PR 和运行 CI。不得启用自动合并；草稿未建好或身份/哈希不符时禁止合并 main。main 的现有 Release workflow 会保留已存在草稿而不重建或公开；若后续需要合并，仍须实测该保护生效。本轮不通过切换 release 标志、修改工作流或提前公开获得安装入口。

现有只读安装渠道主要依赖公开版本历史；本轮不将历史版本的公开试用例外自动扩展到 5.1.2。不为获得安装入口提前公开发布，不自造 NAS 上传/下载接口。后续若没有同包私有/本地安装渠道，必须单独说明这一渠道阻断，再决定如何交付现场试用。

## 第 2、3 步冻结验收清单（本轮不执行）

- 从 NAS 正规 UI 记录宿主与旧插件身份、恢复入口；核对同一候选实际加载版本及资源，保持 AI 关闭、只读开启。禁止 SSH、容器 Shell 或猜接口。
- 真实样本至少含正常电影、正常剧集、缺失或未证实样本、已知错分类样本；首次运行前复核每项当前事实，记录源范围、预期身份与季集、已关联/缺失/错链/待读的逐文件证据。
- 分别评价作品身份是否正确、关系是否可证明、结论是否吻合、是否漏项或误报、覆盖边界、终止/跑完与耗时、错误说明是否可操作。未知不能算正常，超时不能算作品错误，少了问题卡也不等于质量提升。
- 不开 AI 补救覆盖，不点击 execute，不建立、删除或改名任何媒体入口。达不到标准即记录具体缺口，退出该候选，不继续加功能掩盖识别失败。

本地源码、fixture、构建、PR CI 与 NAS 真实样本是不同证据层。只读现场未验前，不宣称识别关通过，更不宣称最终治理目标已实现。
