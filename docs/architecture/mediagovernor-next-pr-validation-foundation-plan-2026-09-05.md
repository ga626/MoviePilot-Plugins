# MediaGovernor 下一阶段 PR：先建立“安装前可证明能用”的验收底座

> 结论先说：**下一阶段不能再发布一个让你安装后才第一次知道效果的扫描版本。**先完成一个不发布、不触碰 NAS 和媒体的“判卷机 PR”。它把我们已经知道的失败案例变成永久测试。只有判卷机和真实宿主的最小加载验收都通过，后续的产品 PR 才允许做候选包、安装和 Release。

这不是拖延功能，而是把“是否真的找对问题”从你的 NAS 前移到开发阶段。否则继续调整现有 `v3.0.0` 的范围、AI 或按钮，只会重复“跑得快但什么都没有”与“跑得久但一堆假问题”之间来回摆动。

## 本次规划的边界

下一 PR 暂定标题：`test(mediagovernor): 建立媒体整理金标准验收底座`。

它只做四件事：建立脱敏样本、固定 MoviePilot 接口替身、把真实前端流程接到样本上跑、生成一眼能看懂的验收结果。它**不**改变扫描策略、不调用 AI、不读取 NAS、不读取真实媒体、不调用 `transfer/manual`、不删除或重建硬链接，也不发 Release、更不要求你安装。

这里必须说清楚：这个 PR 本身不是新的用户功能版本，因此不该把它交给你安装。它的交付是“以后每一个候选版本在安装前必须先通过的判卷机”。真正面向你安装的下一产品候选，只能在它证明已知场景都正确后产生。

## 为什么必须先做它

当前测试主要检查版本、路由、字段、缓存和个别纯规则。它没有把“下载树 → 当前媒体库树 → 历史关系 → 官方预览 → 最终问题卡”完整跑一遍。因此构建成功和页面没有报错，只能说明插件没有立刻崩溃，不能说明它发现了真正失败，也不能说明它识别出表面成功却分错类、错季、错集或错作品。

MoviePilot 的公开 V3 开发文档也把测试定位为：覆盖关键纯逻辑、配置迁移和安全边界；外部网络、真实下载器、媒体服务器和账号应由 mock 或明确的集成测试隔离。它同时要求真实 V3 宿主另验安装、启停/重载、页面/API 只注册一次和 Vue 构建产物。这正好说明：**mock 可以证明逻辑，不能冒充 NAS 验收；NAS 加载可以证明兼容，不能替代判卷。两层都需要。**

Vitest 与 Playwright 官方资料均支持用可复现的假依赖、固定 HTTP 回应或录制回应来驱动测试。这里不录制你的 NAS 数据，也不提交真实请求；只使用手工脱敏的 MoviePilot 回应样本。

## “判卷机”长什么样

每个样本都是一张不含真实路径、文件名、数据库记录或影视库内容的“题目卡”：

```text
下载包的树形摘要
        + 当前媒体库的树形摘要
        + 与该包有关的整理历史摘要
        + 原生识别的确定身份或明确无法确认
        + 官方预览应得的逐文件结果
        = 预期：正常 / 真失败 / 目录分类错误 / 层级错误 / 集号错误 / 身份错误 / 无法确认
```

它不是让测试复述算法：样本同时保存“输入事实”和“人已核对的正确答案”。测试实际运行未来的页面/编排代码，比较实际输出和这张答案。任何算法改动只要漏掉一例、把正常例报成问题、或把无证据例说成正常，测试立即失败，候选不能冻结。

## PR 内要落地的内容

### 1. 脱敏金标准库

新增 `tests/v3/mediagovernor/fixtures/golden/v1/`。每个 JSON 样本带 schema 版本、用途、脱敏输入、预期结论和最少断言；禁止写入真实路径、原始下载名称、媒体库名称、Cookie、数据库 ID 或截图。

第一批至少十例：

1. 原始下载仍在、没有当前目标：`native_failure`。
2. 历史失败但当前目标已存在：正常，不能沿用历史误报。
3. 历史成功、但预览与当前媒体类别不同：`category_error`。
4. 历史成功、但季目录不同：`hierarchy_error`。
5. 历史成功、但逐文件集号对应不同：`episode_error`。
6. 同名动画与真人版：只能返回正确身份或“无法确认”，绝不能自动错选。
7. 一个下载包内部分成功、部分失败：必须切分为独立作品单元，不能被成功项洗白。
8. 手工删改后目标丢失：显示问题或未覆盖，不能静默归零。
9. 目录读取/官方预览失败：`uncovered` 或 `unconfirmed`，不能称“没有问题”。
10. 全部正确的电影/剧集样本：正常且零误报。

样本不追求“代表全世界影视”，只覆盖已经反复让产品失败的合同。今后每发现一次真实新错误，先脱敏成第 N+1 个样本，再允许修代码。

### 2. 单一、可替换的宿主适配边界

把页面当前散落的 `storage/*`、`history/transfer`、`media/recognize_file`、官方预览和手动整理请求，收进一个很薄的 `moviepilotAdapter` 边界。业务编排只调用这个边界；生产实现仍使用宿主传入的 `props.api`，测试实现只按 fixture 返回固定回答。

这不是自创 MoviePilot API，也不改变任何真实请求字段。它只让每一次调用都能在测试里被精确记录：调用了什么、返回什么、是否意外走到 AI/写入路径。适配器的合同由“现有公开 V3 文档 + 当前已使用且经宿主加载过的页面接口”共同冻结；对尚未验证的接口，测试只允许显式 `unsupported`，不得编造成功回答。

### 3. 全链路金标准测试和可见验收页

新增两类测试：

- **后端/合同测试**：在假的 V3 基类与假的 API 下加载插件；确认路由、生命周期、状态脱敏、只读边界和未覆盖状态。现有 Python 合同测试继续保留，不能被新测试替代。
- **前端流程测试**：以假的 `props.api` 挂载真正的 `AppPage` 逻辑，逐个运行金标准样本，验证页面产出的分类、数量、进度、解释、候选禁用状态和执行按钮状态。不是仅测 `governance.js` 函数。

同时生成一个本地静态“验收回执页”（HTML/JSON，作为测试产物，不进 Release）。它只显示样本代号、预期、实际、通过/失败、耗时和未覆盖原因；不含任何真实媒体资料。这样开发者和你都能打开它，看见这一版究竟有没有把十类已知问题找出来，而不必相信一串测试命令。

实现可选 Vitest + Vue Test Utils；若现有 Vite/Vue 组合无法稳定支撑，则改用 Node 测试驱动抽出的页面编排层。选择标准不是“工具看起来先进”，而是能在干净环境稳定执行、输出可见回执。Playwright 只在能可靠启动本地页面时再加；它不是本 PR 的硬依赖。这样不会因浏览器安装或联邦宿主限制，又把基础判卷卡住。

### 4. 不可绕过的候选门禁

增加一个单命令验收入口，例如 `tests/v3/mediagovernor/run_golden.py` 或同等脚本。它必须依次完成：schema 校验、全部金标准断言、无写入/无 AI 调用断言、前端构建、已有版本与联邦 CSS 门禁、生成验收回执。任何一步失败都返回非零状态，且不生成“通过”回执。

门禁应明确检查：

- 真失败、四类假成功和部分成功包均命中；
- 正常样本零误报；
- 读取失败/预览失败只会变成未覆盖或无法确认；
- 同名冲突不能被自动选成单一身份；
- 本 PR 的任何测试运行不调用 AI、官方执行整理或文件删除；
- 输出没有敏感路径或真实媒体资料；
- 页面显示的 `0` 只能表示“全部样本覆盖且全部正常”，不能表示“没有读到东西”。

## 哪些东西仍然不能靠这一个 PR 证明

这个 PR 能证明“对已知题目，未来逻辑确实作出正确判断”；不能证明真实 NAS 的目录接口、MoviePilot 当前镜像或联邦前端一定仍兼容。因此它不替代后续候选的最小真实宿主验收。

反过来，真实宿主验收也不需要拿你的媒体当试题。冻结候选后，只做最小、零媒体写入检查：核对制品 SHA 与版本；安装/加载；打开页面；确认页面 API 被正确注入；确认启用、停用、重载没有重复路由或残留任务；读取插件自己的状态页；确认没有执行 AI、扫描或任何整理。它通过后只说明“候选能在当前 MoviePilot 跑起来”。产品扫描功能仍必须先由金标准证明正确。

任何需要访问真实下载目录、完整扫描或生成修复预览的候选，必须等到后续功能 PR；且只能在新的冻结 SHA、已通过对应新增金标准、并由你明确授权真实 NAS 操作时进行。

## 这次 PR 的完成定义与停止线

完成不是“代码写完”或“测试绿了”。以下全部成立，才允许合并；否则停在分支上修复，绝不创建 Release 或要求你安装：

1. 十个以上脱敏金标准样本齐全，schema 与脱敏扫描都通过。
2. 真正的后端和前端流程均跑这些样本，不是只给 `governance.js` 增加断言。
3. 每一例预期与实际一致；正常样本零误报；未知/未覆盖没有被压成零问题。
4. 验收回执页可打开，明确显示候选源码 SHA、样本总数、通过数、失败数和每项差异。
5. 已有 Python 合同测试、前端构建、版本门禁、联邦 CSS 门禁和 `git diff --check` 都通过。
6. 候选 ZIP 由干净提交生成，并绑定 SHA；冻结后只做一次最小真实 V3 加载验收。若该验收暴露任何合同问题，立即回到新 SHA，不在同一次安装代际临时修补。

第 1–5 条仅让代码“有资格”成为候选；第 6 条才让候选“有资格”进入后续发布。它们都不是对核心产品目标已完成的宣称。

## 后续顺序：何时才会给你安装版本

先完成本 PR 的判卷机，但不发布。之后每一个产品 PR 只能改一层，并且先把对应金标准加进去：

1. **地图与覆盖回执**：确认真实范围、变动与未覆盖，不能再把 47 条历史当问题数量。
2. **作品单元与身份候选**：把一个下载包切成真正可整理的作品单元；AI 只处理压缩后的不确定单元，并能弃权。
3. **官方预览差异审计**：对已确认作品逐文件比较“当前结果”和“官方应有结果”，只显示真实问题。
4. **单项受控重建**：冻结预览后，经你确认，仅由官方路径清理本次对应旧硬链接并重建，再读回核验。

每一层都要先通过判卷机、再走一次冻结候选的最小真实宿主验收。**第一份交给你安装的产品版本，只会在它已经对新增的地图、身份与预览样本全部通过后出现；不会再让你的安装承担“这版到底能不能找出来”的试验。**

## PR 执行清单

1. 从 `main` 新建 `codex/golden-validation-foundation`；先核对工作树干净与当前上游插件合同。
2. 增加 fixtures schema、十个脱敏样本、样本验证器和敏感字段扫描。
3. 抽取并锁定宿主适配边界；生产适配器保持现有公开调用语义，fixture 适配器只读、可记录。
4. 增加后端合同、前端流程和金标准总入口；让每个案例都得到“预期 vs 实际”的机器可读结果。
5. 生成本地可见验收回执页，并在干净环境复跑一次，确认回执不携带真实资料。
6. 运行定向检查，冻结候选 SHA 和同一 ZIP；此时先不要发 Release。
7. 仅在后续获得明确安装/启用授权时，按冻结清单在 NAS 做一次最小 V3 加载验收；任何偏差重新开候选，不在已安装版本上继续试错。

## 证据、推理与缺口

- 当前代码事实：现有 `test_plugin.py` 只加载假基类并检查接口/安全形状；`governance.test.mjs` 只覆盖少量纯规则；`AppPage.vue` 直接编排宿主 API，尚没有整套 fixture 驱动的页面验收。这是本次“先判卷机”的直接依据。
- MoviePilot V3 官方开发文档要求测试覆盖关键纯逻辑与安全边界，外部/真实媒体依赖使用 mock 或明确集成测试；同时要求在真实 V3 确认安装、启停重载、路由注册和前端构建。这支持双层验收，而不是以任一层冒充另一层。
- Vitest 官方 Mocking 文档说明假依赖应在测试间复位；Playwright 官方 Mock APIs 文档说明页面的 XHR/fetch 可用固定回应或 HAR 重放。这支持可复现的前端流程测试，但不构成 MoviePilot 私有接口的证据。
- 未解决的合同：当前宿主是否稳定支持所有计划中的目录、历史、识别、预览字段，仍须在功能层分别冻结并以最小真实宿主验收确认；本 PR 不把未证实字段写成既成事实。
