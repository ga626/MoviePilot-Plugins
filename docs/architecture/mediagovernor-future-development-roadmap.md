# MediaGovernor 后续开发路线：先让结果可见，再让修复可信

日期：2026-09-04。范围：MediaGovernor V3 插件的后续产品、开发、验证与发布路线。

本文是规划与证据报告，不修改产品逻辑，不安装/启用插件，不改 NAS/Docker 配置，不读取或写入媒体、下载、硬链接、数据库、Cookie 或账号资料。

## 先说结论

最终产品方向不变：

```text
下载完成
  -> MoviePilot 原生整理（第一道系统）
  -> 正常且结构正确：结束
  -> 失败，或表面成功但结构异常：MediaGovernor（第二道系统）
       -> 找对作品
       -> 核对整理预览
       -> 仅在以后证明官方执行合同完整时，才讨论受控修复
```

但开发方式必须改变。不能再把「一次完整扫描 + 一次 NAS 安装」当成调试方式；也不能只给出一段绿色终端日志就说功能已完成。

以后每个模块先在本机跑一个**用户可见的验收页**：它同时显示脱敏输入、预期答案、实际结果、调用时间线和通过/失败原因。你先能看懂并认可结果，才进入候选安装。NAS 只保留为最后的宿主合同验证，不再承担日常试错。

## 已确认的现状

### 产品已有的正确边界

- 原生 MoviePilot 是识别、目录规则和整理的主系统；MediaGovernor 只做失败与异常的兜底，不自行移动、删除、重命名或覆盖文件。
- 当前插件已经把 AI 定义为「整包证据的诊断者」，而不是写盘执行者；候选仍需由 MoviePilot 数据源与冲突规则核验。
- 现版本的整理功能停在官方零写入预览。没有旧硬链接的逐项删除清单时，插件不能猜测删除范围或自行清理。

这些边界必须保留，不能为了提高“找到作品”的数量而放宽。

### 当前实现为什么仍不可靠

1. `AppPage.vue` 把库存扫描、包边界、目录取证、模型请求、候选搜索、评分、预览和页面状态揉在同一组件里。它难以单独验证，也容易在一次「开始检查」中把范围、性能和识别错误混在一起。
2. 当前库存扫描把「直接包含视频的目录」当作品包。媒体库父目录、重叠根目录和多季结构会被误判或重复；因此扫描出的数量不是可信的作品数量。
3. 每包可能递归读树、调模型、调多个数据源并查候选详情；当前没有以包指纹复用结果、没有把请求预算当产品合同，也没有先用确定性规则缩小范围。
4. 现有 `tests/v3/mediagovernor/test_plugin.py` 已覆盖版本、只读 API、证据脱敏和少量静态合同，但前端核心逻辑多为「源文件中含某段文字」的断言。它没有验证目录输入最终被分成什么包、动画与真人版如何被区分、候选如何显示、失败怎样提示。
5. 前端 `package.json` 只有 `dev` 和 `build`，没有组件测试脚本。因此当前所谓本地通过，不足以让用户看见实际判断是否正确。

### 已出现且必须回归的真实问题类型

| 类型 | 正确处理方式 |
| --- | --- |
| 历史曾失败、现在已整理好 | 不作为待修作品；只作交叉线索 |
| 媒体库父目录被当成一部作品 | 拆成逻辑包或标为范围错误，不能送模型 |
| 重叠根目录导致重复 | 先做根目录去重与包指纹合并 |
| 同名翻拍、动画/真人版 | 年份、类型、季集、文件集与候选详情冲突时禁止自动确认 |
| 目录无视频、来源不可读、空包 | 归为可解释的非媒体/不可读，不伪装成「没找到作品」 |
| 模型放弃、超时或模型输出不完整 | 记录为模型不可用，继续确定性候选核验；不把普通搜索说成 AI 结论 |
| 表面整理成功但分级/集号错误 | 仅对已确认身份做官方逐文件预览并逐项对照；无完整预览即锁定 |

## 新的验收方式：你能直接看到什么

每个固定样例都是一张卡，而不是一段代码。卡片必须显示：

1. **输入证据**：脱敏目录层级、文件名线索、视频/字幕/NFO 数、已解析集号；不显示真实路径。
2. **正确答案**：例如「动画版、1998、电视剧、第 1 季、应含第 1--26 集」或「不是影视包」。
3. **实际结果**：插件实际分包、模型诊断、原生候选、淘汰理由与最终状态。
4. **结果对照**：每项字段通过/失败；失败写人话，例如「候选为真人版，但输入有 26 集而候选类型/年份冲突」。
5. **时间线**：只显示步骤名、次数和耗时，例如「分包 -> 原生识别 -> 详情核验」，不展示路径、Token、密钥或原始日志。

验收页必须调用和生产页面同一份「纯规则模块」，不能复制一套演示算法。它是给用户看的证明，也是自动测试的输入。

## 分阶段路线

```mermaid
flowchart LR
  P0[PR 0 可见验收底座] --> P1[PR 1 范围与包边界]
  P1 --> P2[PR 2 找对作品]
  P2 --> P3[PR 3 整理正确只读审计]
  P3 --> P4[PR 4 候选验证与发布]
```

### PR 0：可见验收底座（先做，不改变真实业务结果）

**目标**：把能否正确判断，变成可重复、可视化的答案。

**实现范围**：

- 从 `AppPage.vue` 提取无副作用的规则模块：包边界、名称线索、集号解析、候选归并/淘汰、状态分桶、预览完整性检查。
- 建立脱敏 fixture：不含真实路径、媒体文件或用户库名；每个 fixture 都有预期结果。
- 新增后端合同测试：证据规范化、模型 JSON 校验、超时/放弃、隐私边界和只读 API。
- 新增 Vue 组件测试：传入最终 API payload 的 mock，验证进度、范围说明、候选差异、冲突锁定和错误提示。
- 新增本地「验收页/测试报告」：可打开查看所有 fixture 的输入、预期、实际与差异。

**最小 fixture 集**：

| 样例 | 预期 |
| --- | --- |
| 正常单季电视剧 | 正确分为一包，集号连续 |
| 《Cowboy Bebop》动画与真人版冲突 | 不自动确认真人版；明确冲突理由 |
| 同一来源包的多条失败历史 | 合并为一次识别 |
| 已成功的历史残留 | 不列为待修 |
| 父目录含多部作品/多季 | 不当成一个作品 |
| 无视频、空包、来源不可读 | 分别给出非媒体/不可读原因 |
| 重复集、缺集、集号错位 | 整理审计锁定 |
| AI 超时、放弃或乱输出 | 不误确认，仍给出可解释降级 |

**完成定义**：用户能打开验收页，看到每个样例的预期和实际结果；任一错误能精确指出在哪个阶段发生。此 PR 不扫 NAS、不调用真实模型、不修改媒体。

### PR 1：先把检查范围和包边界做对

**目标**：不再把「47 条历史」或一个媒体库父目录误说成当前问题全集。

**规则**：

- 默认范围是用户选择的有限范围（最新整理记录、指定时间窗或指定根）；不默认全库深扫。
- 历史是线索，不是当前事实。当前包是否存在、是否含视频、是否已成功整理，必须由当前可读库存交叉核验。
- 先消除根目录重叠，再用稳定包指纹合并同包记录；包边界不能只凭「这个目录里有视频」。
- 进度从范围建立阶段就显示：读取了多少记录、当前确定了多少包、哪些因权限/上限未覆盖。
- 每一层都有限制：最大目录项、最大深度、最大并发、单包时间预算；达到上限必须标「部分结果」，不能假装全量。

**完成定义**：范围、总数、去重数、未覆盖数和原因全可见；同一包不重复；大父目录不会被投喂给模型。

### PR 2：找对作品（整包证据 + 官方核验）

**目标**：最大化找对作品的概率，但不把猜测当事实。

**顺序**：

1. 本地确定性解析先从包名、代表性文件名、NFO 名称、年份、季集模式中提取强线索；无需模型的情况不消耗模型调用。
2. 只将有预算的整包摘要交给 MoviePilot 当前已配置的模型，要求严格 JSON：作品名、原名、年份、类型、季、预期集号、证据索引、置信度和放弃理由。
3. 用最多两条强线索走 MoviePilot 原生识别、已启用媒体源搜索和详情查询。
4. 统一候选同一作品的不同来源；用原名/别名、年份、类型、季集、视频数和模型结论交叉评分。
5. 信息不足、详情失败、同名翻拍、类型冲突或集数冲突时进入「冲突/资料不足」，只显示可判断的完整资料，不给自动确认。

**完成定义**：动画/真人版、翻拍、同名不同年和季集不符都有 fixture；候选卡展示中文名、原名、年份、类型、季/总集、数据源、命中证据和不能自动确认的理由。

### PR 3：整理正确（只读审计 + 官方预览）

**目标**：确认作品以后，才判断它是否被放对、分级对、集号对。

**前置合同验证**：先在匹配的 MoviePilot V3 宿主上用脱敏/零写入样例确认 `transfer/manual/history`、`transfer/manual/target-path` 与 `transfer/manual` 的字段、预览语义和返回的逐文件计划。当前文档与现有实现对 `reorganize` 参数的表述不完全一致，未验证前不得假设其含义。

**规则**：

- 仅接收 PR 2 已确认身份、且包指纹未变的项目。
- 固定顺序：历史核对 -> 目标规则 -> 官方零写入逐文件预览 -> 预览完整性/重复集/目标唯一性检查。
- 用户看到旧结果摘要、新目标逐文件计划、创建数量、失败/缺项和锁定原因；未通过即不能执行。
- 当前不增加删除、重整或硬链接写入按钮。只有官方未来能提供「预览与删除/创建逐项一致」的合同，才单开设计、候选和明确授权。

**完成定义**：错误分类、错季、重复集、缺项和不完整预览均锁定；正常包明确显示「无需处理」，不制造问题卡。

### PR 4：候选、NAS 验证和发布收口

**目标**：验证同一个候选制品，而不是安装另一份“差不多的包”。

1. 冻结提交与候选 ZIP，记录源码 SHA 和包 SHA。
2. 运行 PR 0--3 的受影响本地测试、构建、版本/联邦结构检查与 `git diff --check`。
3. PR CI 是完整回归权威；CI 失败回到候选修复，候选 SHA 改变后重新执行不可复用的检查。
4. 仅在真实 MoviePilot 宿主加载该候选一次：验证页面加载、只读范围、进度、fixture 对照和官方零写入预览。不做写入。
5. 通过后按 `main -> PR -> CI -> main -> 同一 ZIP -> Release -> 远端下载哈希 -> 稳定安装` 收口。

## 开发环境决定

目前**不建立 NAS 热更新开发线**。原因不是 MoviePilot 没有这种能力，而是当前没有已经验证、可由 Codex 长期自动写入的 NAS 开发目录；若每次变更都要网页上传或人工配置，开发线本身会变成新的不稳定点。

替代方案是「本机可见验收 + 候选宿主验证」：

```text
改一个模块
  -> fixture / 后端合同 / Vue 浏览器组件测试
  -> 生成可见验收页（用户先看输入与结果）
  -> 完整候选制品
  -> 一次真实 MoviePilot 零写入验证
  -> PR、CI、发布
```

未来若出现已授权、可持续的 NAS 开发目录和自动同步通道，才能另开一次小范围可行性验证；它不应反过来阻塞 PR 0--3。

## 未决项与明确停止线

- 当前 NAS 镜像是否完整支持本地插件仓/自动重载：未做配置变更，不作运行态结论。
- 官方手动整理接口是否会在某个参数组合下产生可核验的删除清单：未证明，不设计写入按钮。
- 某个真实失败包的作品身份：没有逐包、可审计证据前，不声称已找到或无解。
- AI 调用的模型、额度、时延与质量：只在 PR 2 以小样例测量；模型不能作为唯一执行依据。

任何一项涉及媒体写入、硬链接清理、目录规则修改、Docker 重建、安装/启用、账号或模型配置时，必须停在该动作前另行取得明确授权。

## 本报告后的第一步

下一项不是继续改识别算法，而是 **PR 0：可见验收底座**。它应先让《Cowboy Bebop》、重叠目录、历史残留、缺集与 AI 放弃等固定样例稳定地红/绿显示。只有这些答案经用户看见并认可，才开始把同一套规则接回 MoviePilot 的真实只读接口。
