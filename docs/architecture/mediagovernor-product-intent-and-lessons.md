# MediaGovernor 产品意图、架构基线与开发复盘

> 状态：产品基线，2026-09-05 重整。本文件定义用户要的结果、现在能证实的能力、不能假装拥有的能力，以及今后每个 PR 的验收门槛。它不是“功能已经完成”的声明。

## 一句话定义

MediaGovernor 是 MoviePilot 原生整理之后的质量保障。它只处理两类事：

1. **原生整理失败**：原始下载还在，却没有得到可核验的媒体库结果。
2. **表面成功但整理错误**：硬链接已经建立，却放错作品、媒体库类别、季目录、集号或文件对应关系。

正常整理仍由 MoviePilot 完成。MediaGovernor 不替代下载器、刮削器或文件管理器；它负责找出真实问题、给出可看懂的预览，并在用户确认后调用 MoviePilot 官方整理流程清理本次对应的旧硬链接、重新建立硬链接、再核验结果。它绝不直接删除原始下载文件。

## 用户要看到的最终闭环

```text
原生整理
  → MediaGovernor 读取当前文件事实
  → 找到真正的问题
  → 确认作品和逐文件预览
  → 用户确认一次
  → MoviePilot 清旧硬链接并重建
  → 再读回，确认实际结果等于预览
```

页面默认只显示问题，不把“历史有多少条”“扫描了多少文件”伪装成问题数量。每一条问题必须说清：哪里错、凭什么说错、当前是什么、正确后会变成什么、会清理哪些旧硬链接。证据不足时必须显示“无法确认”或“未覆盖”，不能显示成正常，也不能自动修复。

## 先统一四个对象

- **下载包**：一次下载留下的一组文件。它可能是一部电影、一季剧、合集，甚至混有多部作品；下载包不等于作品。
- **文件证据单**：这个包当前完整的相对目录树、文件名、上下级关系、文件类型、大小/时间、视频/字幕/NFO 数量、可解析的季集线索及读取是否完整。
- **作品单元**：最终应被整理成的一部电影，或一部剧/动漫的某一季。一个下载包可包含多个作品单元。
- **当前整理结果**：媒体库里实际存在的目标文件和目录；不是历史记录里的旧描述。

要做对，必须先把它们连成关系：

```text
下载包 → 文件证据单 → 作品单元 → 当前整理结果
                   ↘ 已确认身份 → MoviePilot 官方逐文件预览
```

历史记录只是辅助关系，不能替代这条主线。

## 现有版本实际怎么做，以及哪里不可靠

当前已发布 `v3.1.0` 每次建立地图时，会读取下载目录配置、媒体库目录配置、成功历史和失败历史；再读取下载目录的第一层。

它目前把“第一层的一个文件夹”或“第一层的一部视频”当成一个下载包，然后递归读取其内部文件。这个办法不等于识别真实种子：一个种子散落在下载根目录会被拆开；一个顶层文件夹混了多部作品会被合并；多季合集也只能先被当成一个包。因此，**顶层目录只是临时边界，不是可自动修复的可靠边界。**

历史里确实保存了 `download_hash`（下载任务编号）、源文件、目标文件、成功/失败、媒体身份等信息；当前版本却主要以“历史源路径落在顶层目录之下”来归属记录，没有用下载任务编号建立真正的包关系。未来可用同一 `download_hash` 把已有历史的多文件归为同一下载任务；但没有历史的旧文件，现有已核实接口没有提供“目录反查下载任务”的能力。对这类项目只能标记“包边界不确定”，不能靠相似名称硬拼，更不能自动执行。

当前会把目录树整理为文字摘要：文件名、类型、层级、视频数、部分集号、字幕和 NFO 数量。AI 最多看到 500 条条目；NFO 目前只计数量、不读取正文；不会看视频画面、音轨或字幕内容。因而不能说“AI 看完整包后已经确认作品”。完整读取失败或达到上限时，正确状态只能是未覆盖。

当前会读取全部成功/失败整理历史，并以源路径前缀关联。历史一条通常对应一个文件的一次整理，而一季动漫或电视剧会有很多条；用户后来移动、改名或删除文件，历史关系也会过期。因此历史不能用于决定“今天有没有问题”。它只保留两项价值：帮助关联同一下载任务，和在确认修复时定位可安全清理的旧硬链接。

当前还会对每个有关联历史的下载包抽取第一部视频，调用 MoviePilot `media/recognize_file`。这不是重新整理，也不是读取整包证据：MoviePilot 只是从这一个路径和文件名拆标题、年份、季集等文字，再查询它配置的媒体资料来源。原生整理曾因名称不足或同名冲突而猜错时，这一步也可能继续猜错；它只能当候选来源，不能当最终裁判。

原生识别弃权时，MediaGovernor 才把压缩后的文件证据交给自身 AI。用户已关闭“AI识别增强”插件，它不会参与；MediaGovernor 自己的 AI 仍会根据文字结构猜候选。AI 不具备观看视频或证明作品身份的能力，不能直接决定删除、分类或重建。

## 以后唯一允许的判断顺序

### 1. 每次读取目录配置，但不每次全量深扫

每次运行都读取下载区和媒体库的当前配置是必要的：用户调整路径或增加媒体库后，插件才能发现范围改变。配置读取很轻，不应省略。

首次建立地图才递归读取当前下载区和相关目标目录。以后先比较目录指纹；只深入有变化的分支。新整理的完成/失败事件可标记待复核项目，人工移动、改名、删除没有通用广播，只能在下一次对账发现。发现变化后旧预览必须失效，插件不得自作主张把用户删掉的影片补回来。

### 2. 先建立可信包边界，再谈作品识别

包边界按证据强弱分级：

- 同一已知 `download_hash`：可确认属于同一下载任务。
- 同一独立顶层目录、且没有相互矛盾的文件结构：暂定为一个包。
- 散文件、混包、多个作品或缺少任务关系：包边界不确定。

不确定不是失败，更不是正常；它会阻止自动修复，并在界面上让用户看到具体冲突。把一个包再拆成电影或剧集季的作品单元，也必须有目录、集号、候选身份和官方预览共同支持。

### 3. 生成完整文件证据单

证据单保存相对目录树与统计，不把真实路径、Cookie、日志或媒体内容写入 Git、报告或 AI。它必须标明：读取完成与否、是否截断、视频/字幕/NFO 数量、可解析季集、存在的多个标题线索、大小/时间指纹。没有完整证据单，不允许给“正常”结论。

### 4. 历史只作关联与安全回溯

历史用于解释“原文件以前被怎样整理过”“哪个下载任务/旧目标可能与它有关”。它不能决定问题总数，也不能替代对当前下载区和媒体库的读取。旧失败后来恢复、旧成功后来手动移动、源文件因 `move` 不存在，均不能直接当成故障。

### 5. 候选身份由多方交叉核验

MoviePilot 路径识别与 AI 都只能给候选。AI 应接收压缩、去重、分批的完整文件证据，而不是只接收一个标题；同一批可共用规则以节省 token。它必须允许弃权。

候选要变成“可处理的身份”，至少要完成：作品名/原名/年份/类型/季集不冲突，能落到 MoviePilot 可用的数据源身份，并能由 MoviePilot 生成官方逐文件预览。动漫与真人版、翻拍、同名不同年、包内标题冲突、低置信度、预览不完整，都必须停在用户选择页。

### 6. 官方预览定义“应该是什么样”

MoviePilot `transfer/manual` 的零写入预览，才是官方规则下每个源文件应落入哪个库、目录、季集和文件名的权威计算。插件的审计应逐文件比较：

- 当前目标是否存在；
- 当前类别、目录层级、季/集、身份是否与预览一致；
- 哪些旧目标可通过成功历史安全归因。

不能仅用两个标题的字符串比较，就宣称作品放错。

### 7. 只在确认后由官方重建

只有来源仍在、身份已确认、预览完整且未过期、旧目标仍在当前媒体库范围、旧目标与本次成功历史可归因时，才显示“确认重建”。执行必须走 MoviePilot 官方手动整理链路；插件不直接调用通用删除接口，不按名字删，不动原始下载。执行后重新读取源与目标；实际结果和冻结预览一致才关闭问题。

## 问题分类与界面

问题只使用人话分类：原生整理失败、目录分类错误、目录层级错误、剧集对应错误、作品身份错误、无法确认、未覆盖。一个作品可能有多个具体错误，但列表应按作品单元聚合，点开后再展示逐文件差异。

首页只需要：地图是否完整、已覆盖范围、变化数、真实问题数、无法确认数、未覆盖数和真实进度。进入问题后分两步：先确认作品与证据，再看“当前结果 / 官方预览”逐文件对比。没有可用预览时，按钮必须解释为什么不可用，不能做成一个无反应的“查看预览”。

## 上线前必须证明什么

过去已有 20 项合同测试和 14 个虚构金标准案例；它们证明当前规则对人为构造输入的一致性，**不证明**当前分包、真实历史关联、身份确认或 NAS 运行结果已经正确。它们不能再被当作产品完成证明。

每个准备安装的候选必须先通过同一套端到端判卷：

1. 用脱敏样本模拟“目录配置 → 当前下载树 → 当前媒体库树 → 历史关系 → 原生/AI 候选 → 官方预览 → 问题卡”。
2. 样本必须含真实失败类型：散文件、混包、多季、旧失败已恢复、成功但错分类/错季/错集/错作品、手动移动或删除、正常样本、读取不全和身份冲突。
3. 每个样本都写明人工确认的正确答案；测试使用正式编排代码比较预期与实际，并输出可打开的验收回执。
4. 新发现的真实错误，先脱敏成新样本，再修代码。任何关键样本漏报、正常样本误报、未知被说成正常，候选即停止。
5. 判卷通过后，才做最小真实 MoviePilot 宿主加载与冻结验收；真实 NAS 验证只验证同一候选在真实环境的接口、页面、预览与安全边界，不再让用户替插件发现基本逻辑错误。

## 开发复盘：为什么此前反复失败

此前反复出现“几秒跑完却没有结果”“扫描很久却是一堆无关条目”“候选全一样”“检查数和真实问题无关”“预览按钮不可用”，根因不是单一 Bug：

- 先从 47 条失败历史开始，等于先选范围再找事实；它漏掉假成功，也会包含已经恢复的旧失败。
- 后来改为顶层目录扫描，却把顶层目录误当成真实种子和作品边界。
- 用规则过早筛选 AI，漏掉最需要判断的假成功；放宽后又让缺少证据的项目大量进入候选。
- 把“MoviePilot 再按一部代表视频猜一次”误当成“整包证据被重新识别”。
- 把构建、接口调用、页面不报错、虚构样本通过，误当成真实问题已经被找对。
- 在没有冻结判卷合同前连续发布，导致用户安装成了第一轮端到端测试。

这些做法全部废止。以后不得以历史数量作为扫描结果，不得把临时顶层分组说成真实种子边界，不得把 AI 置信度当事实，不得在预览/执行合同未真实验证前声称可安全重建。

## 范围与证据边界

本报告基于当前 `v3.1.0` 插件源码、同仓 MoviePilot V3 的目录、历史、路径识别与手动整理实现，以及本对话的安装反馈重整。它没有读取真实媒体、下载路径、数据库、Cookie 或 NAS 日志；也不把过去的报告、PR 或安装记录当作当前功能已经可用的证明。

外部 KnowledgeRadar 感知入口在本次重整时未注入当前 Codex 对话，因此未把外部搜索内容伪装为本轮证据。后续涉及上游接口变化时，须重新做官方源码/文档核验，并更新本基线的“现有能力”部分。
