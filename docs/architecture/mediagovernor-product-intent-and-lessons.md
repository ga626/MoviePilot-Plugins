# MediaGovernor 产品意图、架构基线与开发复盘

> 本文是本对话及本仓既有设计材料的总基线，不是一次新的功能设计或发布说明。它把用户真正要的结果、目前仍成立的架构方向、已验证的边界和反复失败的模式放在同一处。以后任何 PR 都必须先与本文对照；不一致时先解释并更新本文，不能在实现中悄悄改产品目标。

## 一句话定义

MediaGovernor 不是另一个下载器、刮削器或文件管理器。它是 MoviePilot 原生整理之后的**最后一道质量保障**：只找出真正没整理好、或表面整理成功但实际放错的影视；让用户看清当前结果和应有结果；确认后只通过 MoviePilot 官方流程清掉对应旧硬链接并重建。

这句话比任何当前代码、按钮名称或版本号优先。

## 用户最终要的，不是一个“检查器”

用户要的是一个会长期运行的闭环。

下载完成后，MoviePilot 仍然是第一道整理系统，负责正常识别、分类、命名和硬链接。MediaGovernor 不重复造这套轮子，而是接住两类剩余问题：

1. **真正失败**：原始下载还在，但没有得到应有的媒体库结果。
2. **假成功**：硬链接存在，表面像整理成功，实际却是错误作品、错误媒体类别、错误目录层级、错误季集或错误文件对应。

它的价值不在于把所有文件都展示一遍，更不在于给所有文件生成一个看似聪明的候选；而在于只把有证据的问题交到用户面前。每条问题必须能回答三件事：哪里不对、凭什么说它不对、确认后会怎样修。

最终体验应当是：正常项目默默通过；有问题时出现清楚的原因卡片；用户点进去先确认作品，再看“来源 / 当前媒体库结果 / 官方预览的新结果”的逐文件对照；用户最终确认后，由官方同一整理计划清掉本次确认的旧硬链接并建立新硬链接；然后重新核对，只有实际结果与预览一致才关闭问题。

原始下载文件不是插件的删除对象。用户已有的硬链接策略也不是插件要改写的对象。

## 已经稳定的产品原则

### 当前事实优先，历史只作线索

“47 条失败历史”不是问题总数。历史只说明过去某次整理曾失败或成功，不能证明今天的源文件、目标文件和目录结构仍然是什么状态。系统的判断起点必须是当前下载区和当前媒体库；历史用于补充来源—目标关系、解释和定位可能的旧目标。

同样，显示“0 个问题”必须有前提：本次选定范围完整读完、每个需要判断的项目都得到结论、未覆盖和读失败项目单独可见。否则只能说“尚无结论”，不能说“没有问题”。

### 下载包不等于作品

一个种子或顶层文件夹是下载包，里面可能是单部电影、一整季、多个作品、花絮、字幕或不完整剧集。产品必须从下载包的完整文件结构中再切出可整理的“作品单元”：一部电影，或一部剧/动漫的某季及其集。历史的一条记录也不等于这两个单位，它通常只代表一个文件的一次整理。

因此，长期的数据关系是：

```text
下载包 → 文件集合 → 作品单元 → 当前媒体库结果
                     ↘ 身份核验 → 官方逐文件预览
```

只有这条关系完整，才有资格判断“没整理好”或“整理错了”。

### AI 是身份核验的辅助，不是裁判和执行者

用户确认过，系统应当利用整包的文件名、层级、字幕/NFO、集号和已有冲突信息，而不是只把一个标题交给 AI 瞎猜。这一点成立。

但“先把全库原文一次塞给 AI”不是正确实现：成本高、速度慢、会截断，也容易把同名作品或相邻下载包混在一起。正确做法是先对**所有**下载包建立完整的结构化地图，再把每个无法确定或存在冲突的作品单元以压缩证据卡分批提交。规则在这里负责完整盘点、去重、压缩和找出信息不足/冲突，不能负责宣布“这一定正常”。

AI 只能返回候选、依据和弃权。候选必须回到 MoviePilot 的原生识别取得可用的作品身份，并由官方预览给出逐文件应有结果。动画/真人版、翻拍、年份、季集冲突或低置信度都必须停在用户选择，不得自动重建。若宿主没有稳定的第三方 AI 调用合同，功能应明确降级为“无法确认”，不能猜接口、借用户账号或把模型猜测伪装成事实。

### 官方预览是“应有结果”的权威

文件名相似、目录看起来合理、历史状态成功，都不是整理正确的充分证明。身份确认后，MoviePilot 官方预览才负责算出该源文件应在何处、属于什么分类、怎样命名、每一集如何对应。插件的审计是“当前结果 vs 官方预览”的逐文件比较，不是“标题 A 看起来不像标题 B”。

这使问题类型稳定为：原生整理失败、目录分类错误、目录层级错误、集数/集号错误、作品身份错误、无法确认。最后一类是诚实的产品状态，不是失败提示词。

### 修复必须受控、可预览、可重新核验

用户要的是“一键完成”的感受，不是只收到一句“请去官方手动整理”。但这里的一键不是盲删：它是“确认一次后，由官方完成本次已核实旧目标的清理和重建”。

执行前必须同时满足：来源仍在下载范围、拟处理旧目标可归因到本次成功历史且仍在媒体库范围、身份已确认、预览完整、预览尚未过期。执行使用 MoviePilot 的官方手动整理路径；插件不调用通用文件删除来碰源文件，也不按名字批量删。执行后必须重读真实结果，成功不是接口返回成功，而是实际结果与预览一致。

## 长期运行的架构基线

第一次运行允许慢，但必须做一件真正有价值的事：建立可持久保存的**事实地图**。地图保存的是下载单元、文件集合摘要、作品单元、当前媒体库节点、历史关联、指纹、覆盖状态和问题回执；不是复制视频，也不是把完整媒体路径和文件名暴露给页面或外部模型。

以后不再反复全库扫描：

- 新整理完成或失败时，事件把相关下载包和目标目录标成待复核；多个文件事件先合并为包，再一次读取完整结构。
- 页面打开、低频任务或用户要求复核时，先比对已知目录的指纹；未变化就复用地图，变化部分才深入读取。
- 文件管理器的手工删除、移动或改名没有通用插件广播，不能假装实时知道。下一次轻量对账必须发现变化，并让旧预览失效；用户主动删除的电影不能被插件自作主张补回。

地图、事件和对账三者缺一不可：事件让未来很快，对账补住手工改动，首次地图把插件启用前的旧问题纳入同一事实口径。

当前可依赖的宿主能力是目录配置与列表、成功/失败整理历史、原生识别、官方预览和官方手动整理。明确不能声称的能力包括：从目录 API 证明 inode/硬链接底层关系，以及即时获知所有文件管理操作。产品文案和验收必须保留这些边界。

## 产品界面应当传达的状态

首页不是三个互相重叠的“扫描”按钮。它只需要让用户看到：地图是否完整、覆盖了多少、有哪些变化、当前有多少真实问题，以及本轮进行到哪里。

页面内每个项目只能处于以下之一：

- 正常：当前结果已和官方预览一致；默认不打扰用户。
- 问题：当前事实与应有结果有可解释差异；可进入确认和预览。
- 无法确认：证据不足或服务不可用；不会自动修复，也不会被误说成正常。
- 未覆盖：目录读取失败、尚未扫描或状态已过期；不参与“零问题”统计。

进度必须显示真实范围、完成数、跳过数、待 AI 数、失败数和可继续性。按钮名称必须对应不同工作：首次建图、增量复核、受限全量对账；它们不能都触发同一种全量操作。

## 我们反复犯错的类型

这不是单个代码 Bug，而是一组相互强化的开发错误。

### 1. 把“历史数字”当成了现实范围

从 47 条失败历史出发，使系统先射箭后画靶：历史可能包含已恢复的失败，也会漏掉早已成功但实际放错的内容。后来又为了摆脱历史范围，把筛选压得太严，于是快速跑完却什么也看不到。这两种表现相反，根因相同：没有先建立当前事实地图。

### 2. 把“顶层目录”误当成了可判断的作品

一个包内部分成功、部分失败，或多个作品混在一起时，粗粒度分包会相互遮蔽。于是同一条成功历史能替整个包“洗白”，而错误的季集、分类或身份没有独立对象可以被发现。没有作品单元，就不可能做正确的逐文件预览比较。

### 3. 让规则先决定谁有资格被 AI 看见

为了省 token，曾把 AI 放在“规则已经报异常”之后。这样做确实省了调用，却把最需要 AI 的假成功项目排除在外。后来反向放宽，又产生大量一模一样、缺少原始证据的候选。正确的节省方式是压缩完整地图、缓存未变化包、批量处理不确定单元，不是少看真正需要判断的项目。

### 4. 没有“判卷机”，就直接发版

过去的测试大多验证代码自己写出的规则和接口形状，而不是验证已知错误能否被发现。每一次新的 PR 同时改了范围、分包、AI、UI 或修复路径；NAS 安装后出现问题时，无法判断是哪一层错了。于是用户安装成了真实测试环境，版本号一路增加，目标却没有靠近。

### 5. 把“接口成功、构建通过、页面无报错”误当产品成功

这些只能证明包能构建、API 能调用或页面没崩；不能证明扫描完整、候选可靠、预览正确，更不能证明修复安全。曾出现候选全一样、进度与实际工作不一致、两种扫描按钮做同一件事、地图统计没有回显等情况，都是缺少用户可见的输入—预期—实际对照所致。

### 6. 在没有冻结验收合同前就触碰完整发布链

分支、PR、CI、Release、安装和宿主重启本身可以做得合规，但它们不能弥补产品判断没有验证。发布流程越完整，错误版本带来的安装成本越高。真正应前移的是 fixture、mock、组件验收页和冻结候选的最小 NAS 验证；而不是把更多不确定逻辑塞进下一次大 PR。

### 7. 文档曾经比实现走得更快

此前多份报告已经提出媒体地图、整包证据、官方预览与受控重建；它们描述的是正确方向，不代表当时的代码已经实现或真实 NAS 已验证。以后设计文档必须标清“已证实事实、待验证合同、计划实现”，不能让“有一份完整报告”替代“这一版真的能跑”。

## 从现在起的开发机制

先建立一个不读 NAS、不调真实模型、不写文件的脱敏金标准库。每个样本必须同时包含：原始下载树、当前媒体库树、可脱敏的历史摘要、确认的作品身份、官方预览应有树和预期分类。它必须覆盖真实失败、假成功的错分类/错季/错集/错作品、同名动画与真人版、同名翻拍、部分下载、部分成功包、旧失败已恢复、手工删改、正常样本和越界修复拒绝。

每个改动先在这里运行；测试页要把输入、预期、实际、差异和耗时直接展示出来。只有“已知问题全部命中、正常样本零误报、无法确认不被自动修复”同时成立，才可以进入下一层。随后按固定顺序推进：

1. 地图与覆盖回执；
2. 作品单元与身份候选；
3. 当前结果和官方预览的只读差异审计；
4. 单项受控重建；
5. 同一冻结候选的真实宿主验证与发布。

一次 PR 只允许改变其中一层。发现新问题时，第一步不是调阈值，而是把该问题做成脱敏样本；第二步才修实现。任何 `0 个问题` 都必须携带覆盖、身份核验和预览比较的完成证据。任何真实媒体写入只在预览、最终确认和执行前复核全部通过后发生。

这套机制承诺的是：已知问题不再靠运气反复安装验证，新发现问题会变成永久回归样本。它不承诺仅凭文件名、目录和 AI 就能绝对识别所有未知影视；信息不足时，诚实的“无法确认”才是安全的正确结果。

## 对既有材料的统一解释

本仓较早的范围与安全材料仍有效：插件不替代原生整理、不直接删除源文件、预览和执行分离、AI 不能当执行依据。关于 47 条、耗时、重复候选和《星际牛仔》误识别的运行复盘，仍是问题为何发生的事实证据。事件驱动兜底、媒体地图和产品重建报告，构成目前的正确目标架构。

但所有“单 PR 已完整实现”“全量复核已经能找出真实问题”之类的旧结论都被后续真实安装结果否定，不能继续作为实现完成的依据。当前已发布 `v3.0.0` 只表示安装/加载链曾被打通，不表示用户的两类核心问题已被可靠解决。

## 本文如何使用

新工作开始前，先回答四个问题：

1. 它服务的是哪一条用户最终结果，而不是哪个旧按钮？
2. 它依赖的宿主能力是否已被真实合同验证？
3. 它对应的金标准样本和通过条件是什么？
4. 如果验证失败，系统是明确“未知/锁定”，还是会假装正常或自动修复？

四个问题有任意一个答不上来，就不能进入 NAS 安装或发布收口。

## 考古范围与证据边界

本汇总阅读了当前对话内用户需求与运行反馈、当前会话关联的前序任务记录、本仓架构报告、现有源码测试边界及 Git 提交/发布轨迹。它不读取真实媒体、下载路径、数据库、Cookie 或 NAS 日志，也不重新解释用户已经否定的旧版本为“仍可行”。同名 `.evidence.json` 记录材料、结论和未覆盖边界。
